# GPT-6 Pro 架构评估：摘要与本项目的判断

> 原文存档：`gpt6pro-review-2026-09-19.md`。本文只做两件事：提炼它的核心主张，逐条给出本项目「采纳 / 修正 / 补充」的判断。采纳的内容已写入 `docs/architecture/`，这里不重复展开。

## 1. 它的核心主张

| 主张 | 一句话 |
|---|---|
| 独立建仓，不再造框架 | `drone-agent` 独立于 `embodied-agent` / `cockpit-agent`；复用 Provider、声明式技能、规划执行框架、语音、权限、可观测；不复用机械臂 HAL、halt 语义、座舱任务账本 |
| 四级执行分工 | 任务规划 → 任务执行 → 局部自主 → 飞行控制；安全、证据、数据贯穿 |
| 上层传任务边界，不传每帧动作 | LLM 输出类型化 `MissionSpec`，不是 Python 或 MAVLink |
| 六类契约 | CapabilityDescriptor、MissionSpec、SkillManifest v2、WorldFact/Observation、ExecutionEvent/Evidence、Authority/TaskLease |
| 三元状态 | `execution_status` / `effect_verdict` / `safety_verdict`；`UNKNOWN` 不能包装成成功 |
| 三种世界 | TruthWorld（裁判）/ BeliefWorld（运行时）/ PredictedWorld（候选评估） |
| 安全四道约束 | 任务准入、运行期约束、本地恢复、飞控与人工接管；最终安全判断不交给 LLM |
| 「停止」不是一个 API | 暂停 / 取消 / 失定位 / 低电 / 失联各有平台专用恢复路径；通信心跳、业务活性、观测新鲜度是三件事 |
| 并发与幂等属于物理安全 | 技能声明资源独占；幂等键 = 任务 + 步骤 + 命令 + 设备 + 版本 + 控制权代次；超时后先对账再重发 |
| 空地协同的单位是任务与证据 | 一个协调器分配任务，各机器人本地闭环；首个场景「巡检—发现—复核—报告」；能力发现、空间对齐、任务交接、时空资源预约四项预留 |
| 技术栈 | Python 编排；PX4 + MAVSDK 起步；ROS 2 放适配与局部自主层；Nav2 做地面；PX4 SITL + Gazebo 先行，Pegasus/Isaac 后置 |
| Roadmap M0–M6 | 以「通过什么验证才能进入下一阶段」推进 |
| 评测三分类 | 任务完成 / 合理拒绝或安全中止 / 不安全或错误行为 |
| 定位 | 面向空地异构机器人的安全约束任务运行时 |

## 2. 本项目的判断

### 2.1 采纳（直接进入架构）

以上全部核心主张均采纳。理由：它们与 2026 年前沿系统（Gemini Robotics ER 2 的编排 / 执行分离、P–C–A 综述的「契约 + 校验 + 过滤 + 回退」、RTA/Simplex 安全架构、CoMuRoS 的能力配置化与事件驱动重规划）一致，且针对本人已有代码的具体缺陷（`StepStatus.OK` 掩盖 `UNSAT`、`_replay_prior()` 把「未重发」当成功、halt 闩锁不等于安全状态）给出了可执行的修正。

### 2.2 修正

| 原文 | 修正 | 理由 |
|---|---|---|
| 基础任务先走 MAVSDK，复杂控制「另设明确的适配路径」 | 从 M1 起就只有**一个**控制出口（`guardian` 进程内的 Control Egress），MAVSDK 只是其传输实现；适配器同时声明 `mission_upload` 与 `offboard_*` 两类控制模式，M1 只启用前者 | 仲裁点如果晚建，后期会出现 MAVSDK、ROS 2 节点、技能多头写入 |
| 「机载另起一个安全进程」 | 明确进程拓扑：`executive`（任务执行）与 `guardian`（安全监督 + 控制出口 + 飞控适配）分进程；`guardian` 是唯一持有飞控连接的进程；executive 失效时 guardian 独立执行恢复策略 | 原文只说了「不等于独立故障隔离」，没有给出最小可行的隔离形态 |
| 恢复策略「实现成平台专用恢复策略图」 | 采用 RTA/Simplex 术语：安全监督器 = 决策模块，恢复策略图 = 已验证基线行为集合，且「切回高性能控制器」有显式准入条件（可逆） | 用既有学科语言便于评审、认证与引用 |
| 世界状态「增加显式空间契约」 | `BeliefWorld` 定义为「几何层（局部 ESDF / 占据）+ 语义场景图（资产、异常、观测）」，两层都携带坐标系、地图版本、时间与协方差 | 多机器人场景图是空地共享世界表示的当前最优实践 |
| 没有法规接入 | 准入层增加 `AirspaceConstraintProvider` 插件点（UOM 报备 / 空域属性 / Remote ID） | 国内 2026-05-01 起未登记锁飞；真机（M4）前必须接入 |
| 没有讨论 MCP / A2A | MCP 只用于规划层只读工具；A2A 用于 `cockpit-agent` → `drone-agent` 的任务入口；两者都不允许触达控制出口 | 社区 ROS 2 MCP 服务器普遍直接发布 `cmd_vel`，必须明确禁止 |
| 厂商扩展只举了「有的只开放航线」 | 明确第二平台优先级：DJI Cloud API（国内市场、Dock 自动化）> ArduPilot（AP_DDS 原生）；两者都通过能力协商接入 | 面向国内低空经济场景 |
| Roadmap 无时间尺度 | 给出按 1–3 人团队的指示性周期与并行研究线 | 用户需要可排期的 roadmap |
| MAVSDK-Python 未指明版本 | 锁定 MAVSDK-Python 3.17.x（`>=3.17,<5`）；v4 原生绑定上游已文档化但 2026-09-17 尚未上 PyPI，发布后只迁适配器 | 包名与 API 正在变，不按实际发布状态锁定会踩迁移坑 |

### 2.3 补充

1. **证据验证的分工**：确定性检查（位姿有效、时间有效、目标 ID 匹配、影像清晰度阈值）判定「完成」；VLM 判定只做「疑似异常 / 任务进度」的业务判断，并带置信度进入证据，不参与安全判定。
2. **影子运行是学习型技能的唯一入口**：`LocalPolicy` 插件先以只记录不执行的方式跑满评测集，再有限接管。
3. **契约测试是跨项目共享内核的前提**：原文提出「机械臂与无人机跑通同一份契约测试后再抽 `agent-kernel`」，本项目把这组测试命名并放在 `tests/contracts/`，作为 M0 交付。
4. **仿真分线补充**：空地联合仿真优先用 PX4 SITL 同时跑多旋翼与 rover（PX4 v1.17 支持 rover 模式与 Ackermann SIH）在同一个 Gazebo 世界里，避免早期对接两个仿真器。
