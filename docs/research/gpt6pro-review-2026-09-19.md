## 先给结论

**我建议新建独立的 `drone-agent` 仓库，但不要再造一套完全独立的 Agent 框架。**

更合理的组织方式是：

> **应用独立、通用契约逐步统一、控制与安全按本体分别实现、空地协同通过任务和世界状态连接。**

具体来说：

| 你的问题 | 我的建议 |
|---|---|
| 合并到 `embodied-agent`，还是独立？ | **独立。** 无人机在持续执行、故障处置、空间表示、飞控接入和评测方面，需要独立的领域边界 |
| 现有项目怎么复用？ | 优先复用 Provider、声明式技能、规划执行框架、语音交互、权限、可观测；**不是原样复用机械臂 HAL、停止逻辑或座舱任务账本** |
| 如何兼顾前沿和扩展性？ | 用“任务规划—任务执行—局部自主—飞控”分层，给 VLA、世界模型和多机调度保留受约束的插件接口 |
| 空地协同怎么做？ | 先做“一架无人机发现、一台地面机器人复核”，共享任务、空间事实和证据，不共享底层运动控制 |
| 第一阶段做什么？ | **先做无大模型的单机仿真安全闭环，再接入大模型生成任务。** 不从集群、端到端 VLA 或完整微服务系统起步 |

我查看了两个仓库的 README、具身项目的架构与迁移文档，以及 HAL、世界状态、执行器、技能声明、控制服务和座舱任务账本等关键实现；也核验了截至 **2026 年 9 月 19 日**可检索的代表性研究和官方技术文档。以下是架构级静态评审，没有在本轮运行仓库测试或进行实飞验证。

下面以**民用多旋翼、园区/设施巡检、仿真先行、单机逐步扩展到空地协同**为设计假设，不预设某一家整机厂商一定开放全部控制接口。

# 一、为什么我建议独立，而不是直接合并

## 1.1 无人机属于具身智能，但不意味着必须放进同一个仓库

从概念上看，无人机当然是具身智能的一种本体。问题不在于“分类是否属于具身智能”，而在于：

**你现在的 `embodied-agent`，已经做到哪一层的跨本体抽象？**

它的设计目标是跨本体运行时，但当前落地主要围绕桌面操作机器人展开：MuJoCo 仿真、机械臂抓放、学习策略替换、感知与独立真值评测；真机和更广泛本体仍在后续路线图里。这说明它已经有值得继承的框架，但不能直接等同于成熟的通用机器人 SDK。fileciteturn1file0L2-L2

更关键的是，实际代码里仍有明显的机械臂语义。

| 我在代码中看到的现状 | 对无人机项目的影响 |
|---|---|
| `control/hal.py` 的观测包含 `qpos`、`qvel`、`gripper_opening`、`ee_pose`；动作包含 `joint_targets`、`gripper` | 这不是添加一个 `PX4Driver` 就能自然适配的通用动作接口。无人机需要飞行模式、位姿、速度、定位健康度、能源、任务进度等类型化状态。fileciteturn8file0L2-L2 |
| `cognition/world_state.py` 的世界快照包含末端位置、夹爪和抓取关系 | 需要保留“世界状态验证”的思想，但重新设计空间、时间、不确定性和多机器人状态。fileciteturn11file0L2-L2 |
| 控制服务在监督链路失效时闩锁 `halt`，阻止继续写入动作 | 无人机不能把“停止写入”直接等价成“进入安全状态”；还需要结合飞行阶段、定位、能源和飞控模式决定后续行为。fileciteturn12file0L2-L2 |
| 当前架构把多机器人调度列为后期能力，初始部署围绕单机三进程组织 | 无人机项目若把任务协同作为明确目标，需要更早设计跨设备的任务、权限、状态与资源契约。fileciteturn4file0L2-L2 |

所以，我不建议通过增加大量 `if embodiment_type == "drone"`，把无人机塞进当前机械臂接口。

**这会让“跨本体”变成各类特殊分支的集合，而不是稳定抽象。**

## 1.2 还发现了两个不能直接迁移的执行语义

这部分值得单独强调，因为它会直接影响新项目的设计。

### 第一，诚实汇报失败，不等于阻止错误的后续执行

当前 `embodied-agent` 的 `cognition/executor.py` 中：

- 验证结果为 `UNSAT`、采用报告策略时，可能只记录 `_verify`，仍保留 `StepStatus.OK`。
- 对此前超时的相同动作去重时，`_replay_prior()` 可能返回 `OK`，同时用说明文字提示没有重新执行。
- 后续依赖步骤主要依据 `StepStatus.OK` 决定是否运行。fileciteturn15file0L2-L2

这些逻辑在迁移到无人机前必须重新定义。比如：

> “起飞命令超时，但没有重复下发”不等于“已确认起飞完成”，更不能据此进入下一段航线。

建议拆成三类状态：

```text
execution_status：命令是否被接受、执行、结束
effect_verdict：预期物理效果是否已被证实
safety_verdict：当前是否允许进入下一阶段
```

只有满足该阶段规定的证据要求，才放行后续动作；`UNKNOWN` 不能被包装成成功。

### 第二，座舱长任务账本也不是飞行任务控制器

我读取的 `cockpit-agent/agents/_sdk/ledger.py` 明确为异步调研等长任务设计：取消通过心跳拉取，建议心跳间隔不超过约 10 秒；数据库不可达时采取 best-effort 降级，任务仍可继续执行。这对分钟级调研任务是合理的权衡，却不能直接作为飞行任务的取消与控制权机制。fileciteturn18file0L2-L2

无人机需要另设**本地权威任务状态和即时控制通道**。云端账本可以暂时不可用，但不能因此失去本地取消、安全恢复和控制权仲裁。

## 1.3 推荐的仓库关系

我建议保留三个独立应用：

| 仓库 | 建议长期职责 |
|---|---|
| `cockpit-agent` | 座舱产品、多模态交互、车内外服务；也可以成为经过授权的机器人任务入口 |
| `embodied-agent` | 当前操作机器人能力，以及后续地面本体适配；验证通用任务与技能契约 |
| `drone-agent` | 无人机任务、飞行技能、载荷、飞控适配、飞行安全、空地协同场景 |

**通用内核应当逐步提炼，而不是现在立刻启动第四个“大一统平台项目”。**

起步时可以选择性迁移小模块，记录来源版本并带上测试；等机械臂和无人机都跑通同一份契约测试后，再抽出版本化的 `agent-kernel` 包。

未来依赖方向应当是：

```text
embodied-agent ──依赖──▶ agent-kernel
drone-agent   ──依赖──▶ agent-kernel

agent-kernel 不依赖 PX4、MuJoCo、机械臂驱动或车辆 VAL。
```

短期可以先在某个仓库内维护可独立发布的包，不必马上新增仓库。重要的是**单一维护源、版本化依赖和明确边界**，不是仓库数量。

只有当你的目标只是“给具身项目增加一个无人机研究样例”，而不是持续发展的无人机产品时，我才会更倾向于合并。

# 二、前沿研究应该参考什么，又不能照搬什么

我不建议选择某一篇论文，照着它搭完整项目。更有效的做法是区分：**任务生成、局部自主、世界模型、协同、数据生成**，分别吸收适合的设计。

以下是本次核验后，我认为与你最相关的代表性工作。

| 方向与代表工作 | 对你的架构有价值的部分 | 不应直接推导出的结论 |
|---|---|---|
| **ARIES-Mission2，2026-08**：视觉语义与航路优化分离 | 自然语言解析、目标接地之后，由专门优化器处理访问顺序；适合借鉴为“语义任务→确定性任务编译” | 生成较短航路，不等于已经解决避障、动态约束或失联恢复。citeturn368292academia13 |
| **DreamFly，2026-08**：历史记忆、滚动规划、显式终止 | 摘要提出预测一段动作、只执行第一步再观察；将终止判断从动作生成中分离 | 基准上的导航终止判定，不等于安全着陆或飞行安全保证。citeturn368292academia12 |
| **LAUS，2026-07**：面向无人机集群的 Agent 架构 | 将感知、记忆、规划、执行纳入闭环，并讨论机载/边缘算力、间歇网络和认知链路攻击 | 它是架构提案与研究分析，不是可以直接部署的成熟集群运行时。citeturn605309view1 |
| **WorldFly，2026-06**：世界模型与动作联合建模 | 给未来的预测模型保留接口，用于候选行动评估和局部导航 | 模型预测的未来画面不能成为“当前真实世界”的权威来源。citeturn368292academia15 |
| **CosFly，2026-05**：规划空间与渲染空间解耦 | 适合参考为专家轨迹、合成数据和评测场景生成链路 | 其数据构建流程不是已经验证过的实机在线自主飞行栈。citeturn304884view3 |
| **AutoFly，2026-02**：无人机 VLA 导航 | 说明视觉语言策略可以承担局部导航能力，适合放进可替换的 Policy 层 | 论文实机部署把模型放在远端服务器，通过局域网回传速度指令；不能据此假设模型已完全机载、离线可靠。citeturn605309view0 |
| **Hierarchical Language Models for…Aerial-Ground Robotic System，2025，后续修订** | 空中机器人提供全局语义信息，地面机器人执行局部导航和操作，值得参考其功能分工 | 特定任务的仿真与实机实验，不代表任意异构设备都能直接接入。citeturn605309view3 |

我的综合判断是：

> **面向工程落地，最值得采用的不是“让大模型直接飞”，而是“让大模型表达目标，让局部自主系统持续完成目标，让独立控制与安全机制约束全过程”。**

你应当同时保留两条技术路线：

**工程主线：** 声明式任务＋确定性执行＋传统/成熟局部规划＋飞控。

**研究支线：** VLA、世界模型、学习型局部技能；先影子运行和离线评测，再有限度接管。

这样既不会错过前沿，也不会让整个系统的可用性取决于某一代模型。

# 三、推荐架构：不是“大脑—驱动”两层，而是四级执行分工

## 3.1 总体结构

我建议核心采用：

> **任务规划 → 任务执行 → 局部自主 → 飞行控制**

安全、证据和数据贯穿其中。

```text
┌──────────────────────────────────────────────┐
│ 操作者：Web / 平板 / 语音 / 座舱入口           │
│ 任务输入、范围确认、进度、接管、证据报告       │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│ 任务与协同层：可在地面工作站，也可在云端       │
│ LLM/VLM Planner · 技能目录 · 地图/知识工具     │
│ Fleet Coordinator · 任务账本 · 权限审批       │
└──────────────────────┬───────────────────────┘
                       │ 类型化 MissionSpec
                       ▼
┌──────────────────────────────────────────────┐
│ 确定性任务编译与准入                         │
│ 参数/能力/空间/时间/资源校验 · 审批版本绑定    │
└──────────────────────┬───────────────────────┘
                       │ 已授权任务包
        ┌──────────────┴──────────────────┐
        ▼                                 ▼
┌──────────────────────┐      ┌──────────────────────┐
│ UAV 机载运行时       │      │ 地面机器人运行时     │
│ Mission Executive    │      │ Mission Executive    │
│ 技能生命周期管理     │      │ 技能生命周期管理     │
│ 感知/定位/局部地图    │      │ 感知/定位/局部地图    │
│ 局部运动规划/策略     │      │ Nav2 / 操作技能      │
│ 控制权仲裁与指令校验 │      │ 本体专用安全控制     │
└──────────┬───────────┘      └──────────┬───────────┘
           ▼                             ▼
   PX4 / 厂商飞控适配器              底盘 / 机械臂适配器
           ▼                             ▼
   飞控原生控制与故障保护              本体控制器

贯穿：安全监督、观测证据、任务事件、数据记录、回放与评测
```

这里最重要的区别是：

**上层传递的是任务及其边界，不是依赖公网连续下发的每一帧飞行动作。**

## 3.2 各层分别负责什么

### A. 任务规划层：理解“要做什么”

例如用户说：

> “检查 A 区三处设备的外观，发现疑似异常后安排地面机器人复核，最后给我带照片的报告。”

LLM 可以负责理解目标、拆解任务、选择能力、解释异常和提出重规划。

但最终输出应是类型化任务，而不是任意可执行 Python，也不是原始 MAVLink 命令。

我建议它输出：

```text
目标：完成三处设备外观巡检
对象：asset_01、asset_02、asset_03
空间范围：已批准的 inspection_volume_A
完成要求：每个对象具备位置与时间绑定的有效影像
协同规则：疑似异常进入地面复核队列
恢复规则：触发平台指定的 recovery_policy
```

**LLM 可以提出扩大巡检范围，但不能自行扩大已批准的飞行范围。**

### B. 任务执行层：负责长时间、有状态的任务

你已有的 DAG 适合表达任务依赖，但不应该独自承担全部飞行生命周期。

建议组合：

**任务 DAG 管依赖；状态机或行为树管持续执行和恢复。**

例如一个 `inspect_asset` 节点，内部可能持续数十秒甚至更长，需要处理接近、观察、图像质量检查、补拍、取消和退出。这不应只是一个等函数返回的黑盒。

执行器至少需要：

```text
accepted → preparing → running → verifying → completed

中间可能进入：
pause_requested / paused
cancel_requested / recovering / cancelled
blocked / failed / outcome_unknown
```

特别注意：

**“用户取消了任务”与“飞行器已经进入安全状态”必须是两个不同的事件。**

### C. 局部自主层：负责“此时此地怎样完成”

这一层处理定位、障碍、轨迹、短期目标和平台约束。

它可以有两种技能实现：

| 实现 | 建议定位 |
|---|---|
| 确定性/传统实现 | 初始默认路径，例如预验证航线、局部轨迹规划、受约束巡检 |
| 学习型实现 | 后续插件，例如视觉语言导航、主动选取观察角度、局部语义搜索 |

两者向下提交相同类型的**候选局部目标或轨迹**，通过同一套约束检查。

不要让“换成 VLA”意味着绕过原来的权限、超时、空间约束和证据系统。

### D. 飞行控制层：交给专用飞控

我不建议你自研姿态控制、角速度控制和电机分配，也不建议让通用 Agent 运行时承担这类实时闭环。

工程起点可以选择 PX4，并以适配器隔离。对于后续 ROS 2 集成，PX4 的 Control Interface 已包含命名模式、模式执行器、解锁检查和故障状态机集成；官方文档同时说明部分接口仍具有实验性质。因此适合预留接口，但应锁定并验证具体版本组合，而不是直接跟随主分支。citeturn750619view0turn368292view1

# 四、最应提前设计好的，是六类契约

未来扩展性主要来自契约，而不是目录里提前建立几十个空模块。

| 契约 | 建议包含的核心内容 | 解决的问题 |
|---|---|---|
| **CapabilityDescriptor** | 设备身份、真实可用技能、支持的控制模式、传感器、载荷、限制、接口版本 | 防止上层假设所有无人机或机器人能力相同 |
| **MissionSpec** | 目标、对象、空间/时间范围、依赖、能源预算、恢复策略、审批版本 | 将自然语言变成可验证、可执行的任务 |
| **SkillManifest v2** | 参数、前置条件、持续约束、资源占用、进度、取消语义、完成证据、失败恢复 | 支持长时间物理技能，而不只是工具调用 |
| **WorldFact / Observation** | 位置、坐标系、时间、来源、不确定性、有效期、证据引用 | 避免把陈旧、预测或不确定的信息当事实 |
| **ExecutionEvent / Evidence** | 命令接受、执行状态、物理效果验证、失败原因、关联影像与遥测 | 防止“调用成功＝任务成功” |
| **Authority / TaskLease** | 机器人、任务版本、控制权代次、有效期、命令序号、资源占用 | 防止重复执行、旧指令重放和多个控制源争用 |

## 4.1 不要把无人机状态继续塞进 `extras`

建议通用观测只保留公共头：

```text
robot_id
timestamp
frame_id
schema_version
source
valid_until
```

载荷则按本体明确区分：

```text
AerialState
GroundMobileState
ManipulatorState
```

共享的是时间、身份、证据与任务语义；不是强行让无人机也有 `gripper_opening`。

## 4.2 将“世界”明确拆成三种

这是我认为你应该同时落实到两个具身项目中的抽象：

| 世界表示 | 谁使用 | 能否作为当前事实 |
|---|---|---|
| **TruthWorld**：仿真真值 | 评测裁判、标注、分析 | 不能偷偷提供给被测 Agent |
| **BeliefWorld**：感知与估计得到的世界 | 运行时规划、技能执行 | 可以使用，但必须携带时间和不确定性 |
| **PredictedWorld**：模型预测的未来 | 候选动作评估、研究策略 | 不能冒充当前观测 |

你的具身项目已经在感知输入与仿真真值裁判分离上建立了基础，应继承这个方向。fileciteturn1file0L2-L2

但无人机还应增加显式的空间契约：坐标系、海拔参考、姿态约定、时间同步、定位协方差和地图版本。**座舱导航拿到的一个地图点，不能未经坐标和误差校验就直接成为飞行目标。**

## 4.3 将“任务完成”定义成可检查的证据

例如：

```text
到达航点 ≠ 完成设备巡检
拍了一张照片 ≠ 拍清楚了指定设备
识别出异常 ≠ 异常已经被地面机器人复核
发送返航命令 ≠ 已经完成返航着陆
```

每个技能应声明自己的完成条件。

`inspect_asset` 的条件可以是：目标身份匹配、影像质量达标、观测位姿有效、时间有效、证据已关联到对象。具体阈值属于场景配置，不由 LLM 临时生成。

# 五、安全体系必须按飞行重新设计

## 5.1 不要设计成一个“安全 Agent”

可以有模型辅助分析风险，但**最终安全判断和控制权不能交给另一个 LLM**。

我建议分为四道约束：

**任务准入约束。** 检查任务是否落在批准的设备、空间、时间和能力范围内，确认参数、资源和恢复条件。

**运行期约束。** 持续检查定位、能源、空间边界、传感器有效性、轨迹有效性和控制权。

**本地恢复机制。** 上层规划不可用时，由本地执行器按照已验证的恢复策略处理，而不是等待模型回答。

**飞控与人工接管。** 保留飞控原生故障保护和独立接管路径。机载另起一个安全进程，不等于已经获得独立的供电、计算和通信故障隔离。

## 5.2 “停止”不能只定义成一个通用 API

建议把用户语义与平台动作分开：

| 用户/任务语义 | 系统应当决定的内容 |
|---|---|
| 暂停任务 | 是否具备安全等待条件，等待多久，之后进入何种恢复路径 |
| 取消任务 | 如何停止业务动作并进入经过验证的恢复流程 |
| 失去定位 | 哪些模式和恢复方式仍然可用 |
| 能源不足 | 还可到达哪些已验证安全位置，剩余余量是否足够 |
| 失去通信 | 继续已授权任务、等待或恢复的条件是什么 |

不能固定理解成“异常就悬停”或“异常就返航”，更不能把空中断开电机当作普通取消行为。

建议把这部分实现成**平台专用恢复策略图**，并用故障注入逐个验证。

## 5.3 一个容易漏掉的故障：SDK 还在发，业务控制已经停了

MAVSDK 官方文档说明，Offboard 插件会自动以 20Hz 重发设定值；PX4 的 Offboard 存活要求则包含持续的最低频率信号。citeturn605309view2turn368292view2

由此带来的设计风险是：

> 控制业务已经卡住，但 SDK 仍在重发旧设定值，飞控看到的链路可能仍然“活着”。

所以不能只监测“连接是否断开”。

建议独立检查：

```text
最新观测是否仍有效？
最新轨迹是否仍有效？
当前控制任务是否仍健康？
控制权租约是否仍有效？
```

过期动作必须进入已定义的恢复路径。**通信心跳、业务活性、观测新鲜度是三件事。**

## 5.4 并发和幂等也属于物理安全

已有 DAG 会并行执行同层步骤。迁移后，必须防止同一架无人机同时运行两个争用运动控制的技能。

建议每个技能声明资源，例如：

```text
uav_01.motion：独占
uav_01.gimbal：按技能组合规则占用
uav_01.camera：按拍摄模式占用
```

命令幂等也不能只靠“技能名＋参数”判断。应使用任务、步骤、命令、设备、版本与控制权代次的组合标识。

**网络超时后的正确动作首先是状态对账，而不是自动重发。**

# 六、哪些可以从已有项目沿用

你的主要积累确实能显著降低启动成本，但复用重点应当是**工程模块与验证方法**。

既有迁移文档也明确区分了模块移植与部署拓扑，并记录了“带测试迁移、标注来源、不复制密钥、不建立整仓运行时依赖”的规则。这套规则值得延续。fileciteturn16file0L2-L2

| 资产 | 优先来源 | 复用建议 |
|---|---|---|
| 多模型 Provider、超时、限流、健康检查 | `embodied-agent/providers`；对照座舱最新实现 | **优先复用。** 保留轻依赖，避免顺带搬入整套网关服务 |
| Planner、结构化计划、参数引用、技能检索 | `embodied-agent/cognition` | **保留框架，重写飞行相关执行语义。** 尤其是 UNKNOWN、验证失败、并发、取消和恢复 |
| SkillManifest、Registry | `embodied-agent/skills` | 扩展为长时间技能契约，加入持续约束、资源占用与抢占规则 |
| ASR/TTS/S2S、多轮交互、用户确认 | `cockpit-agent` | 复用成熟交互能力，但语音只提交任务请求；声纹不能单独作为飞行授权 |
| HMI/Android 的任务进度和确认交互 | `cockpit-agent/hmi`、`mobile` | 复用交互逻辑，重做任务地图、控制权和飞行状态呈现 |
| 权限、审计、隐私、日志与追踪 | 两仓库相关模块 | 复用机制，重定义 scope、设备权限与数据保留范围 |
| 任务账本与幂等设计 | 座舱 `agents/_sdk/ledger.py` | **参考业务账本，不原样作为飞行控制账本**；增加本地权威状态、版本和恢复对账 |
| Episode、独立裁判、基线回归 | `embodied-agent/data_engine`、`eval` | 复用数据与评测方法，重定义飞行传感器、时钟和任务证据格式 |

不建议直接搬运的部分包括：

**机械臂运动学、夹爪/关节动作、桌面抓取判据、现有 halt 语义、车辆 VAL 内容、车控规则，以及完整座舱微服务拓扑。**

尤其不要因为两个项目都有“位置”概念，就复用同一套空间数据；也不要因为都有“取消”按钮，就复用同一套取消实现。

### 我建议的抽包时机

在无人机完成基础任务闭环后，选择一组公共契约，让机械臂和无人机共同运行测试：

```text
规划输出可验证
技能调用有明确生命周期
依赖动作必须等待效果证实
不确定结果不能变成成功
未授权动作无法通过执行出口
```

这组测试通过后，再把相应实现迁到 `agent-kernel`。

**公共内核是被两个真实场景验证出来的，不是靠提前猜测所有机器人长什么样设计出来的。**

# 七、空地协同应该怎样落地

## 7.1 协同的单位应该是任务与证据，不是聊天消息

第一版不需要每架无人机、每台地面机器人都运行一个大模型，更不需要让它们通过自由对话协商控制动作。

我建议：

> **一个协调器负责分配任务，每台机器人维护自己的本地执行与安全闭环。**

空地协同研究中，“空中获取全局语义，地面执行局部导航与操作”已经有具体实验路径；对你来说，值得借鉴的是这种互补分工，而非复制某一套模型组合。citeturn605309view3

## 7.2 第一个完整场景：巡检—发现—复核—报告

建议用下面的场景贯穿架构、仿真和评测：

> “无人机完成园区设备巡检，发现疑似外观异常后生成空间标注；地面机器人到达附近进行近距离复核，最后合并两端证据。”

完整链路应当是：

```text
用户提交巡检目标
    ↓
协调器检查设备能力与可用资源
    ↓
无人机执行空中巡检
    ↓
生成 ObservationRecord
  对象ID、位置、坐标系、时间、不确定性、图片、疑似异常
    ↓
生成地面复核任务
    ↓
地面机器人确认可达性并接收任务
    ↓
近距离重新定位对象、拍摄、复核
    ↓
证据合并；分别报告已完成、未完成和不确定部分
```

这里，地面机器人必须重新判断局部可通行性。**空中看起来有路，不等于底盘可以通过。**

## 7.3 四项协同能力需要提前预留

| 能力 | 第一版就需要的设计 |
|---|---|
| **能力发现** | 哪台设备能飞、能走、能拍热成像、能近距离观察；同时考虑当前能源、载荷、定位与通信状态 |
| **空间对齐** | 地图版本、坐标变换、时间、误差和证据来源；没有可靠对齐时不能交付一个看似精确的目标点 |
| **任务所有权与交接** | 明确谁接收、谁执行、何时超时、何时确认交接，防止重复作业和任务丢失 |
| **时空资源预约** | 降落区、狭窄通道、观察位置等共享资源的占用，以及机器人失联时如何保留保守边界 |

**控制权和地图事实不应使用同一种一致性策略。**

地图和观察可以允许迟到更新；但谁正在控制某台机器人、哪个任务版本有效，必须有明确的权威与旧指令拒绝机制。

还要注意：租约过期只是软件状态，**不代表失联的机器人已经在物理世界中停止**。在重新分配冲突任务前，需要考虑其最后状态与可能继续执行的范围。

## 7.4 你当前的具身项目还不能直接充当地面移动机器人

当前已落地的主要是操作机械臂。要支持真正的地面移动协同，需要增加移动底盘适配、定位地图和导航技能，而不是把桌面机器人换个名字。fileciteturn1file0L2-L2

我建议地面导航采用 Nav2 适配器。Nav2 已提供行为树组织、规划器/控制器插件、恢复行为和导航任务接口，适合作为地面局部执行栈；你的 Agent 负责任务语义与协同，不必重新实现一套地面导航。citeturn605309view4

但不要把地面二维导航能力直接当作无人机三维避障能力。

# 八、具体技术栈与未来扩展

## 8.1 起步技术组合

| 层面 | 我的建议 |
|---|---|
| 任务规划和编排 | Python，延续你已有 Provider、结构化计划和测试体系 |
| 单机任务状态 | 本地持久化状态＋事件日志；云端数据库不进入飞行实时依赖链 |
| 首个无人机适配器 | PX4；基础任务先走 MAVSDK 等任务/遥测接口，复杂自主控制另设明确的适配路径 |
| 感知与机器人集成 | ROS 2 放在适配与局部自主层，不要求通用 Agent 内核直接依赖所有 ROS 消息 |
| 飞行控制写出口 | 一个明确的控制权仲裁点；不能让 MAVSDK、ROS 2 节点和多个业务技能同时争用 |
| 地面机器人 | ROS 2＋Nav2 适配器；操作机械臂继续复用既有技能体系 |
| 操作界面 | 专用任务控制台，结合已有语音与 Android 交互能力 |
| 评测 | 契约测试＋故障注入＋SITL 集成测试＋独立任务裁判 |

这里有一个具体取舍：

**MVP 的预规划任务与后续局部自主飞行，不必强行使用同一种控制模式。**

前者可以由飞控执行已验证任务；后者需要局部规划器持续提供受约束的目标。通过统一任务与技能接口向上屏蔽差异，但不能在下层隐藏不同模式的实际能力限制。

## 8.2 仿真要分成两条线

**飞控与系统验证线：PX4 SITL＋Gazebo。**  
优先验证真实飞控逻辑、模式变化、遥测、任务状态、通信异常和多设备集成。PX4 官方仿真文档将 Gazebo 作为重要集成路径，并提供不同仿真方式的选择。citeturn750619view1

**感知与学习数据线：后续按需求引入高保真环境。**  
例如 Pegasus 提供基于 Isaac Sim 的无人机仿真及 PX4 集成，可以作为后续候选；CosFly 则适合参考其数据生成流程。它们不应成为第一阶段跑通任务闭环的前置条件。citeturn750619view2turn304884view3

已有 MuJoCo 可以继续承担机械臂基线和部分研究原型，但不能替代对选定飞控运行时的集成验证。

第一版空地联合仿真，我更倾向于让 UAV 和 rover 在同一个可同步的场景里运行，而不是过早连接两个大型仿真器、再处理时间和空间同步。

## 8.3 数据格式不要只围绕训练模型设计

建议原始数据保留多频率传感器和飞控日志，训练数据集只是其派生视图。

每次任务应能关联：

```text
任务与审批版本
模型 / 策略 / 软件 / 飞控配置版本
观测时间与坐标变换
动作与控制模式
安全干预
实际任务结果
原始影像与遥测证据
```

可以设计 MCAP/rosbag2、飞控日志与任务事件的关联记录，再按需要导出 LeRobot 等训练格式；不要为了统一模型输入，将所有原始飞行数据强制压成一个采样频率。

模型升级也应绑定版本：先回放、仿真、影子运行和受限场景验证，再切换正式策略。**不建议在飞行过程中在线自我训练或无审批热换策略。**

## 8.4 厂商扩展应当是“能力协商”，不是统一假接口

未来接不同厂商时，有的平台可能开放连续控制，有的只开放任务上传、航点、相机或云台。

因此 `CapabilityDescriptor` 应说明实际能力和限制。缺少某种能力时，上层应调整计划或明确拒绝，不能用看起来相同的接口掩盖实现差异。

这也适用于未来固定翼、VTOL：不能把多旋翼特有的等待或运动方式当作所有飞行器的默认行为。

# 九、建议的 Roadmap

我建议按“通过什么验证才能进入下一阶段”推进，而不是按“演示界面已经能动”推进。

| 阶段 | 核心交付 | 退出标准 |
|---|---|---|
| **M0：领域边界与基础契约** | 独立仓库、MissionSpec、Skill 生命周期、控制权与证据契约、复用清单 | 通用代码与飞行代码分离；禁止模型直达控制出口的契约测试建立 |
| **M1：无大模型的单机闭环** | PX4 SITL：起飞、预验证航线、采集、恢复、着陆；任务记录与回放 | 独立裁判判断结果；超时、重复指令、模式变化和取消等故障测试通过 |
| **M2：接入受约束 Agent** | 自然语言→任务草案→确定性校验→审批→执行；有界重规划 | 模型给错坐标、能力、参数或任务顺序时，无法绕过准入；不确定执行不进入依赖步骤 |
| **M3：局部自主与降级** | 感知/定位接口、局部地图、短期规划、能源与恢复策略、机载部署形态 | 观测过期、控制任务卡住、网络中断、计算过载等场景行为可验证 |
| **M4：两条验证线并行** | A：单机受限真机验证；B：一架 UAV＋一台 rover 的联合仿真 | A 验证接管和故障保护；B 完成任务交接、空间对齐、复核证据闭环 |
| **M5：真实空地协同** | 在明确授权和受控范围内完成巡检—复核—报告 | 不把部分完成说成全部完成；设备失联、退出或任务交接失败时能正确收敛 |
| **M6：模型与平台扩展** | VLA/世界模型插件、第二飞行平台、多机调度、数据迭代 | 相同任务和裁判下证明新增能力有价值，同时没有不可接受的安全与可靠性退化 |

学习模型的研究可以提前并行开展，但不要让它成为 M1～M4 工程主线的前置条件。

## 9.1 评测不能只有“任务成功率”

建议从第一阶段就把结果分成三类：

**任务完成、合理拒绝/安全中止、不安全或错误行为。**

否则系统可能靠拒绝所有任务获得“零事故”，也可能靠虚报成功获得高成功率。

重点指标应包括：

| 维度 | 建议指标 |
|---|---|
| 任务质量 | 目标完成率、覆盖度、有效证据比例、错误成功报告数 |
| 物理安全 | 碰撞/越界、最小间隔、能源余量违反、安全干预 |
| 实时与可靠性 | 控制周期尾延迟、陈旧指令拒绝、观测过期处理、故障恢复结果 |
| 空地协同 | 交接成功率、重复执行、任务丢失、空间标注误差、复核完成率 |
| 工程成本 | 人工接管频率、模型费用、算力和存储占用、复现成本 |

初期可以建立固定场景和多随机种子测试集，并要求所列关键故障场景全部通过。但**有限测试集里的零违规不是实飞安全证明**，后续仍要扩大场景、环境和故障覆盖。

## 9.2 最先做的，不应是一大批空模块

第一批提交建议聚焦四个实物产出：

1. **架构与安全边界文档**：明确 LLM、执行器、适配器、飞控分别能做什么。
2. **可执行契约与测试**：明确 accepted、completed、verified、unknown 的区别。
3. **一个无 LLM 的 SITL 任务闭环**：能运行、能取消、能注入故障、能给出证据。
4. **选择性迁移记录**：每个复用模块的来源、修改点、测试和后续维护归属。

先把这些做扎实，再扩充 UI、模型、技能数量和设备类型。

## 最后，我对这个新项目的定位建议

不要把它定义成：

> “支持用语音控制无人机的 Agent。”

这个定位容易变成“语音识别＋几个飞控 API”的封装。

我更建议定义成：

> **面向空地异构机器人的安全约束任务运行时：将自然语言目标编译为可验证任务，在本地约束内执行、按真实证据确认结果，并支持任务交接与协同。**

以无人机作为新项目的主要落地领域，但把任务、技能、证据、权限和设备协同的契约设计成可共享。

**这样，你的三个项目不是三个重复的聊天入口，而是三种场景对同一套“理解—执行—验证”能力的逐步验证；真正按本体区分的，是控制、安全和物理世界建模。**
