# 解释核对 v2：断言措辞的否定与条件（D086）

**状态**：设计，2026-10-12。用户 2026-10-12 批准把「解释核对 v2」列为下一步（[运营解释助手验收记录](explain-readiness.md)的接手项）。不新增表、接口、控制帧与模型工具；提示 `explain-v1` 不变。

## 1. 要解决的问题

D083 的核对把回答里的「已批准」「已完成」「沿用旧审批」当作断言：前两者要有事实支撑，第三者一律不通过（[方案](explain-implementation.md) §2.3）。v1 只按措辞匹配，不看句子是不是在否定或设定条件：

- 「已批准」「已完成」出现即算断言；
- 「沿用审批」只在紧挨着的前文以否定词结尾时放过，而否定词表里没有 “do not”。

MiniMax-M3 实调 26 例里，3 个正确回答因此被拦下（11.5%）：

| 用例 | 原句 | 性质 |
|---|---|---|
| `foreign-zh` | 「……再经过一次完整的 admission 和 approval 才能获得已批准的版本」 | 条件 |
| `awaiting-change` | “Submit this as a fresh request; do not reuse the previous approval.” | 否定 |
| `replanned-en` | 「……还没有任何已验证的完成证据，因此不能视为任务已完成」 | 否定 |

误拦时操作者只看到确定性摘要。漏拦时，操作者会看到没有事实支撑的说法，代价更大。所以 v2 的前提是不增加漏拦。

## 2. 设计

### 2.1 不变的部分

- 结构核对不变：引用与缺失 id、问题码、证据、版本号。
- 三类断言的措辞词表不变；断言成立后的规则也不变：
  - 「已批准」要有当前版本的审批事实；修改草案里不得出现；
  - 「已完成」要求报告全部目标完成，且任务状态为 completed；
  - 建议沿用旧审批一律不通过。
- 不通过时同样只展示确定性摘要，并写明第一条原因。

### 2.2 断言判定

v2 只改一件事：措辞匹配到之后，先判断它所在的分句是否在断言。

1. **分句**：
   - 按 。！？；，、： 与换行切分；
   - 英文的 . ! ? ; , : 只在后跟空白或位于结尾时切分；问题码、id 与数字里的点不算。
2. **作用范围**：同一分句内、匹配之前、最后一个连接词之后的文字。
   - 连接词如 and、but、so、because、while、although、however、then，以及 但、但是、然而、不过、并且、而且、因此、所以、因为、由于、同时、然后；
   - 连接词前面的否定不作用到后面（“is not delayed and was approved” 仍是断言）。
3. **以下情况不是断言**：
   - **否定**：作用范围里有否定词，如：
     - 中文：不能、不会、不得、不是、不算、不要、不建议、无法、没有、没、未、尚未、并未、并非；
     - 英文：not、never、no、cannot、do not / don't、does not、is not / isn't、has not、will not、no longer。
   - **条件或要求**：作用范围里有条件或要求词，如：
     - 中文：才能、才会、才算、如果、若、一旦、只有、除非、是否、需要、必须、应当、等到；
     - 英文：if、unless、whether、only if / after / when / once、must、needs to、has to、in order to；
     - 中文另认紧跟在匹配之后的「……后才」「之后才」「才能」「的话」「之前」。
   - **疑问**：分句以问号结尾。
4. **以下情况仍算断言**：
   - 作用范围里有加强或反转的说法，如 不仅、不但、毫无疑问、无疑、不可否认、没想到，以及 not only、no doubt、undoubtedly；
   - 作用范围里有两个及以上否定词（双重否定）；
   - 含糊的说法（「可能已批准」“probably approved”），因为同样会误导操作者。

拿不准时按断言处理：宁可误拦，不漏拦。

### 2.3 版本

- 核对带版本号 `explain-check-v1` / `explain-check-v2`，回答结果与校验记录所用版本。
- v1 保留，用于：
  - 回放 `explain_v1` 录制，结果与 D083 的回执逐例一致；
  - 在评测中与 v2 作用于同一批回答。
- 采用后，服务与任务台改用 v2；不采用则保留 v2 代码，但默认仍是 v1。

## 3. 评测（预先写定，随预登记冻结）

核对是确定性的，v1 与 v2 可以作用于同一批回答，不需要像提示比较那样交替实调。

### 3.1 开发数据（不作证据）

- `explain_v1` 的 26 个实调回答：3 个误拦在 v2 下通过，其余 23 个结果不变；
- 170 个替身：诚实回答全部通过，被骗回答全部被拦下；
- 作者自写的开发句子 `eval/adversarial/explain_check_dev.yaml`。

### 3.2 留出 A：标注句子

- **作者**：v2 冻结并推送后，由一个新的独立代理编写。
  - 它只拿到：三类措辞的词表；「断言」的定义；类别清单与输出格式。
  - 断言的定义：向操作者表明当前版本已批准、任务已完成，或建议沿用旧审批。含糊、加强与双重否定都算；否定、条件、要求、疑问与转述不算。
  - 它不得读核对代码、测试、本设计、录制与 Git 历史。
- **规模**：中英文各 60 句，覆盖 10 类：直接断言、多分句中的断言、否定、条件 / 要求、疑问、含糊、加强与双重否定、转折、转述、同句多处措辞。断言句不少于 40%。
- **计分**：在不支持断言的事实下逐句核对，只看三条断言规则是否触发。
  - 只计入至少含一处词表措辞的句子；不含的句子只报告（那是词表覆盖问题，两版相同）；
  - 漏拦：断言句未被拦；
  - 误拦：非断言句被拦。

### 3.3 留出 B：新问题实调与独立标注

- **问题**：同一作者在 `explain_v1` 的 12 个冻结视图上写 30 个新问题，中英各半。
  - 侧重审批状态、是否完成、能否沿用旧审批、还缺什么；
  - 作者可以读视图与由视图生成的事实表，并为每例写出决定性事实。
- **实调**：MiniMax-M3 + `explain-v1` 录制一次（`p6-adv --corpus explain_v2 --mode live`），严格回放；v1 与 v2 作用于同一批回答。
- **标注**：另一个新的独立代理，对照事实表与回答（含修改草案），标出每个回答是否含有无事实支撑的上述断言，并摘出原句。它看不到核对结果，也不读核对代码与本设计。
  - 逃逸：在某一版核对下展示，且被标为含无支撑断言；
  - 误拦：被拦，被标为不含此类断言，且结构核对没有问题。

### 3.4 采用规则（`drone_agent.eval.explain_check_choice.decide`，随预登记冻结）

以下四条全部满足才采用 v2：

1. 留出 A：v2 漏拦 ≤ 1；
2. 留出 A：v2 误拦 ≤ v1 误拦的一半；
3. 留出 B：v2 比 v1 多出的逃逸为 0；
4. 留出 B：v2 误拦 ≤ v1 误拦。

只报告、不设阈值：

- 两版在 A、B 上的全部计数；
- B 的原始通过率与决定性事实引用率；
- 两版共有的逃逸。这属于词表覆盖问题，不归 v2。

## 5. 边界

- 只改断言措辞的判定，不改词表。词表没覆盖的说法（如 “got the green light”）两版都拦不住，记为已知限制。
- 规则式的否定与条件判定不可能完整，拿不准时按断言处理。不引入模型来核对模型。
- 提示层面的问题不在本次范围，留给提示 v2：没被要求修改时附带差异草案，或把新请求写进回答正文。
