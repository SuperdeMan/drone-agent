# 资产时空证据档案设计（WP-P6-04）

**状态**：2026-10-13 按 D087 准出（候选 `6249129`，[验收记录](asset-archive-readiness.md)），软件 / SITL 范围。用户 2026-10-12 批准 WP-P6-04 的表结构变更（「下一步要做的我批准」），表结构见 §5。

## 1. 结论

操作者要问的是：「这次和上次不同，是维修、角度，还是新异常？」今天这个问题只能部分拼出来：

- 没有资产实体，也没有逐资产的时间线；
- 证据里只记了拍摄位置，没有航向；
- 维修反馈是自由文本；
- 改了站点地图，旧采集的几何也会悄悄跟着变。

本设计新增三张只追加的表：

| 表 | 内容 |
|---|---|
| 资产修订 | 按站点地图内容摘要快照资产定义 |
| 资产观测 | 每次核验过的采集一条，含按位置实测的视角 |
| 资产事件 | 复核、工单、维修、结算与参考图的权威时间线 |

在此之上提供确定性的差异比较：

- 两次采集之间资产定义是否变化、视角是否一致、期间是否有维修与复核结论；
- 每一项都附证据 id；
- 模型的判断单列为「模型推测」，从不进入事实，也不参与比较。

不引入图数据库，不改既有表与列，只在既有 JSON 正文里加可选字段。

## 2. 现状要点

调研结果见本节；路径以 `src/drone_agent/fleet/` 为基准。

- **资产定义**：在站点地图 YAML 里（位置、尺寸、相机、观测航线），没有逐资产的版本。
  - 地图版本标签不唯一，例如 `campus_v2` 被多个站点共用；
  - 真实身份是内容摘要，按任务版本封入 `RunHeader.registry_sha256`，但地图正文不进账本；
  - 再分析时读的是当前地图。
- **采集**：`evidence.captured_pose` 只有位置，`orientation` 从未填写，航向只是航线的声明值。
  - 尺度、偏移、可见比例只在 `bz_jobs.result.quality` 里；
  - 参考图的拍摄位姿与质量没有记录。
- **业务链**：发现 → 复核 → 工单 → 维修反馈（自由文本，至多 300 字）→ 复检 → `reinspection-v1` 结算。
  - 转移历史只在 `op_events` 里；
  - 发现正文会被覆盖，证据与持续项都有上限；
  - 复检期间的任何疑似结果，都作为「仍异常」挂到工单的发现上，不看类别。
- **逐资产读取**：只有 `analysis.media`，而且扫描项目的全部任务；store 已有按资产的读取，但没有对外提供。
- **模型输出**：`facts` 中的 VLM 信念，以及作业的 score / defect_type / description，都是模型输出。权威来源是：人工复核、结算结论、服务核验、管理员登记的参考图，以及配置。

## 3. 设计

### 3.1 权威等级

档案的每条记录都带 `authority`：

| 等级 | 来源 | 例 |
|---|---|---|
| `fact` | 配置、服务核验、人工操作 | 资产定义快照、采集核验、复核决定、维修登记、参考登记 |
| `decision` | 服务按确定性规则对输入作出的决定（输入可能含模型输出，一并记录） | 复检轮次结算 |
| `belief` | 模型或分析器的判断 | 分析作业的判定与分数、由疑似结果开出的候选发现 |

接口按等级分栏返回。`belief` 只出现在「模型推测」栏；比较的各项因素只由 `fact` 与 `decision` 计算。

### 3.2 资产修订

- **主键**：`(asset_key, registry_sha256)`，`asset_key` 沿用业务层的 `<project>/<scope>/<asset>`。
- **快照内容**：种类、位置、尺寸、相机、观测航线（航点）、`above_asset_m`、所在体积与坐标系（`frame_id`、地图版本标签）。
- **写入时机**：服务加载站点地图时，为每个资产写一条快照，摘要相同则不重复，首次出现记 `first_seen_at`。从此地图正文中与资产有关的部分进入账本。
- **旧摘要的正文**：任务用过、但已不是当前地图的摘要，若仓库的站点地图（`configs/scenarios/`）中有内容摘要相同的文件，就用它补成修订：摘要相同即正文相同，不是推测。找不到正文的旧摘要不编造，关联的观测标为「定义未知」，比较时这一项给出 `unknown`。
- **之后才找回的正文**：已迁移的账本在每次打开档案时做同样的补齐（只追加修订）。此前写入、视角为「定义未知」的观测不改；读取时若其定义已能找回，就用证据中的拍摄位姿当场算出视角，并标明 `definition_recovered`。

### 3.3 资产观测

- **写入时机**：服务写入采集核验（`service.py` 中两处 `record_verification`）时，若该步骤以资产为目标，就在同一事务里写一条观测，主键是 `evidence_id`。资产取任务包中该步骤的目标资产，而不是机器人自报的对象。
- **内容**：
  - 任务、版本、步骤、拍摄时间、媒体摘要；
  - 地图摘要（取该版本的 `RunHeader`）；
  - 服务核验判定与各项检查，并记下这次核验所用地图的摘要（回填时不可知，记为 `null`）；
  - 补拍来源（若由补拍产生）。
- **核验变化**：服务每次刷新都会用当前地图重新核验。观测写入后不改；之后若用**同一张地图**的核验改变了判定或检查（例如机载判定晚到且不一致），追加一条 `verification_changed` 事件，读取时以最后一次为准。换了地图之后的重新核验不算这次采集的核验，档案不跟随。
- **视角**（确定性，按位置实测）：资产位置取同一摘要的修订，与采集位置在同一坐标系时计算：
  - 到资产中心的距离；
  - 从资产看采集点的方位角与俯仰角；
  - 坐标系不同或修订未知时为 `unknown`。

  证据没有姿态，这里假定相机对准资产，这正是 `inspect_asset` 的语义。声明航向只作参考列出，标明 `declared`。观测只存实测值，是否可比由比较容差决定（§3.6）。
- **图像测量**：尺度（目标边长像素）、偏移、可见比例取自同一证据的 quality-v2 分析作业。读取时按 `evidence_id` 关联 `bz_jobs`，不复制；它们是确定性的图像测量，属于 `fact`。同一作业的判定与分数属于 `belief`。

### 3.4 资产事件

只追加，与业务转移在同一事务中写入。`source_key` 唯一，重复提交不会重复写入。

| 事件 | 等级 | 写入点 |
|---|---|---|
| `finding_opened` | belief | 疑似结果开出或并入发现（含复检中挂到工单发现上的「仍异常」），正文标明是否新开 |
| `finding_confirmed` / `finding_dismissed` | fact | 发现复核 |
| `order_opened` | fact | 确认后建立工单 |
| `repair_reported` | fact | 维修反馈（`orders.repair`），含结构化维修内容（§3.5） |
| `round_reviewed` | fact | 复检轮次的人工复核（确认或否定修复） |
| `round_concluded` | decision | 复检结算（passed / failed / unknown），附结算依据：作业来源与判定、复核 |
| `maintenance_recorded` | fact | 工单之外的维护登记（§3.5） |
| `reference_registered` / `reference_revoked` | fact | 参考图登记与撤销 |
| `revision_seen` | fact | 资产定义的新快照首次出现 |
| `verification_changed` | fact | 同一张地图下的核验结果改变（§3.3） |

`op_events` 照旧，档案事件是按资产索引的权威副本。事件 id 由 `source_key` 的摘要得出，回填与在线写入对同一业务转移得到同一条事件。迁移时从业务表回填（§3.8）。

### 3.5 结构化维修

- **随维修反馈提交**：`orders.repair` 增加可选的 `repair` 对象：
  - `action`：repaired / replaced / cleaned / adjusted / other；
  - `part`：至多 80 字；
  - `performed_at`：不晚于提交时刻。

  它存进轮次反馈的 JSON（`bz_rounds.feedback`），不改列。原有的 `note` 不变，不带 `repair` 的旧调用行为不变。
- **工单之外的维护**：新写接口 `assets.maintenance`，权限与 `orders.repair` 相同（`WORKFLOW_RUN`）。它只写一条 `maintenance_recorded` 事件，不开工单、不启动复检。

### 3.6 差异比较（确定性）

**接口**：`assets.compare(project_id, asset, evidence, against)`。

- `evidence` 缺省为最新一条核验通过的观测；
- `against` 缺省依次取：该观测之前最近一次登记的有效参考图的采集；没有参考图时，取上一条核验通过的观测。

**因素**（每项都附证据 id，都只由 `fact` / `decision` 计算）：

- **定义**：两条观测的地图摘要是否相同；不同时列出资产定义中变化的字段（位置、尺寸、航线）。
- **视角**：以比较容差判断是否一致，任一项超出即「视角不同」；坐标系不同或定义未知时为 `unknown`。
  - 距离比、方位角差、俯仰角差；
  - 方位角只在两次采集的水平距离都不小于 `bearing_min_horizontal_m` 时比较：相机几乎正对资产上方时方位角没有意义，此时俯仰角与距离已能区分视角；
  - 有图像测量时，再看尺度比（目标边长像素之比）与偏移差（两次偏移各除以本次目标边长后的差）。
- **期间事件**：两次拍摄时刻之间的维修、维护、复核与结算。
- **参考**：`against` 是否为有效参考图，以及它是否在期间被撤销。

**模型推测单列**：两条观测上分析作业的判定、分数与缺陷类型，标明分析器与来源。

**摘要**：服务按因素生成确定性的中英文摘要。它只陈述因素，不下「是维修 / 是角度 / 是新异常」的结论。例如：

> 两次采集之间登记了 1 次维修（工单 X 第 2 轮，replaced 防护罩）；视角一致（距离比 0.97，方位差 4°）；地图未变；模型推测：本次正常。

**比较容差**：版本化配置 `configs/analysis/compare_v1.yaml`，回答中带其摘要。初值：

| 项 | 初值 |
|---|---|
| 方位角差 | ≤ 15° |
| 方位角参与比较的最小水平距离 | 1.0 m |
| 俯仰角差 | ≤ 10° |
| 距离比 | 0.8–1.25 |
| 尺度比 | 0.8–1.25 |
| 偏移差 | ≤ 目标边长的 25% |

### 3.7 接口与权限

| 方法 | scope | 说明 |
|---|---|---|
| `assets.list` | `ANALYSIS_READ` | 项目内资产，各带最近一次观测与未结发现数 |
| `assets.timeline` | `ANALYSIS_READ` | 修订、观测与事件按时间倒序，带游标分页；按权威等级分栏 |
| `assets.compare` | `ANALYSIS_READ` | §3.6 |
| `assets.maintenance` | `WORKFLOW_RUN` | §3.5 |

- 新方法加入授权矩阵（`eval/p5_authz.py`）。
- 读取走 `(asset_key, 时间)` 索引，不扫描任务。
- `orders.repair` 的参数从「精确集合」改为「必需参数加可选的 `repair`」；其他方法的参数仍是精确集合。
- 入口：运营台服务端增加只读帧 `asset_timeline` 与 `asset_compare`，转发到上面两个方法，供入口核对；页面不变。

### 3.8 迁移与回填

- **迁移方式**：`meta.asset_schema = 1`，新增三张 `ar_` 表及其索引，并给 `bz_jobs (evidence_id)` 加一个索引。与 D056–D085 相同：先在线备份并校验，DDL、回填与标记在同一事务内提交。只在带业务目录时执行；`desk-cloud --apply` 先在账本副本上演练。
- **执行时机**：资产键的范围取决于调度目录（共享坐标时为 `*`），所以档案在服务装配完成（业务引擎与调度器都已挂上）之后打开：先迁移与回填，再为当前站点地图记录修订（摘要已有则不写）。演练入口直接读运营与调度目录，用同一条范围规则。
- **回填内容**：
  - 当前站点地图的资产修订；`first_seen_at` 取使用该摘要的最早任务版本的 `RunHeader` 时间，没有任务用过时取迁移时刻；
  - 任务用过的旧摘要中能在仓库站点地图里找到正文的，同样补成修订（§3.2），归属该任务绑定的项目与站点；
  - 有绑定的任务中，已核验且以资产为目标的采集，补成观测；修订找不到正文时，视角为 `unknown`；
  - 由业务表的现有状态与时间推出事件：发现、复核、工单、轮次（反馈、复核与结论）、参考图、修订首次出现。
- **回填约束**：
  - 确定性：回填只依赖账本、当前目录、仓库中的站点地图，以及迁移时刻；事件 id 由来源键得出。两份副本在同一时刻迁移，档案内容逐字节相同；已迁移的账本再迁移不改变任何东西。
  - 不改其他表：演练核对其余对象的摘要不变。

## 4. 不变量

- 档案只追加；观测与修订写入后不改。
- 档案不改变任何业务判定：发现、工单、结算与可派遣性照旧，删掉档案不影响它们。
- 模型输出只进 `belief`。`fact` 栏与比较因素中不出现任何模型字段，由测试钉住。
- 比较是只读的纯函数，同样的账本得到同样的结果。
- 不编造缺失的数据：定义、坐标系、图像测量缺失时，如实给出 `unknown`。

## 6. 评测（写定后再实施）

- **S0**：在 P6 任务台世界中构造以下场景，每个场景对 7 / 19 / 41 三个种子判定。
  - E1 维修：确认的发现 → 工单 → 带结构化维修的反馈 → 复检正常 → 比较复检采集与上次疑似采集。期间事件含这次维修，视角一致。
  - E2 角度：同一资产两次采集的位置超出方位或距离容差，期间无维修。比较给出「视角不同」及数值，不归因于维修。
  - E3 新异常：同一视角、期间无维修，分析器判疑似。比较只列出「定义未变、视角一致、期间无维修」与模型推测，不下结论。
  - E4 定义变化：两次采集之间换了站点地图中该资产的位置或尺寸。比较给出定义变化与变化字段。
  - E5 隔离：改写某次作业的模型判定，`fact` 栏与比较因素不变；`belief` 栏照实变化。
  - E6 回填：在业务账本的两份副本上于同一时刻迁移，档案内容相同；再迁移一次不变；其余对象摘要不变；回填的观测数等于以资产为目标的已核验采集数。
- **回归**：P1–P6 S0、授权矩阵（含新方法）、长稳裁判单元测试。
- **任务台**：激活时迁移并回填真实账本。经入口对任务台上的资产读时间线并做一次比较；常驻 SITL 采集的位置是真实遥测，视角因素在真实数据上可算。
- **门禁**：`scripts/verify_asset_archive.py`。判据：
  - 范围、云端检查；
  - 当场重跑 S0 场景与回归；
  - 迁移演练与回填；
  - 任务台激活、入口与时间线；
  - 先前记录不变。

## 7. 不做

- **实测航向与姿态**：需要改机载适配器（属于 M1 回归范围），留待 H 系列。本设计用位置推出方位与俯仰。
- **资产上的缺陷定位**：发现仍按资产与类别聚合。同簇先后发现的关联只体现在时间线上。
- **自动归因**：服务只给因素，不判定「是维修 / 是角度 / 是新异常」，也不用模型做归因。
- **解释助手覆盖资产**：D083 只覆盖任务。资产事实表可作为后续扩展的输入。
- **页面**：本次只做接口与入口核对。资产时间线页面另立。
- **图数据库、媒体去重与清理**：不做。
