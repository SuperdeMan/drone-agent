# P6 设计稿：主动补拍与目标区域质量（WP-P6-02，待评审）

[路线图](roadmap.md) · [实施任务 §10](operations-implementation.md) · [评审记录](research/external-review-2026-10-10.md) · [P4 记录](p4-readiness.md) · [运营架构](architecture/09-operations.md)

**状态：设计稿，待用户评审（D078）。** 用户 2026-10-10 选定 P6 先做主动补拍；按约定先给出设计与决策，评审通过后才改代码。本稿不修改任何门禁状态。

## 1. 要解决的问题

现在的闭环是「拍照 → 分析 → 看不清 → 拒判，等人处理」。拒判原因已经存在（`quality.blurry`、`quality.exposure`、`analysis.undeterminable` 等），但只能让节点失败、运行以未知结束，系统不会利用这些原因补救。

评审建议：把失败信息转成有边界的下一步动作。首版不允许自由移动，只在已登记拍摄位重采；补拍次数与资源有预算；超出原授权要重新审批；补拍失败仍可保持未知；模型只能给原因，不能生成飞行指令。验收目标是在遮挡、模糊与不良角度场景中降低拒判或人工接管比例，且不增加错误判定。

## 2. 现状核对

| 事实 | 位置 | 对设计的约束 |
|---|---|---|
| 质量层 `quality-v1` 只看整张图的分辨率、亮度、截断比例与梯度清晰度 | `fleet/analysis.py::check_quality` | 背景清楚不代表目标清楚；需要目标区域 |
| 采集证据带拍摄位姿 `captured_pose`，资产登记有位置与尺寸 | `contracts/events.py`、站点地图 `assets.*` | 目标区域可由位姿 + 资产几何 + 相机模型投影得到；相机内参目前没有登记 |
| P4 分析作业被拒时，`analyze_evidence` 节点以带原因的失败结束 | `fleet/workflow.py`、`business.py` | 下游 `requires: success` 的节点被跳过，运行以未知收尾 |
| 条件只有 `suspected` / `decision` 两种输出，谓词只读**已完成**节点的输出 | `workflow_models.py::Predicate`、`predicate_holds` | 失败节点的原因不能作条件，需要内核扩展 |
| 模板是无环 DAG，节点数有上限 | `WorkflowSpec` 校验 | 补拍只能按固定次数展开，不能循环 |
| 每次飞行都要人工审批（D032），领取闸门重查可派遣性与预约 | `service.py`、`dispatch.py` | 补拍是一次新的任务，沿用全部审批与派遣规则 |

## 3. 设计

### 3.1 目标区域质量（`quality-v2`，新的质量画像版本）

- **几何**：站点地图为每个相机登记针孔模型（分辨率、水平视场角、安装外参），作为新的版本化字段，由契约测试钉住。目标区域是资产外包盒（位置 + `size_m`）按采集位姿投影到图像上的矩形。
- **测量**：目标可见比例（投影矩形在画面内的面积比）、目标尺度（矩形短边像素）、目标区域内的亮度 / 截断比例 / 梯度清晰度。
- **拒判原因**（新增，均为 `quality.*`）：`quality.target_out_of_frame`、`quality.target_too_small`、`quality.target_blurry`、`quality.target_exposure`。
- 位姿或相机模型缺失时以 `quality.target_unknown` 拒判，绝不退回整图检查给出结论。
- 限值只在 S1 / S0 的渲染上标定，像 `quality_sim_v1` 一样写进画像，改任何限值即新版本。`quality-v1` 不变，已固定它的运行继续有效。

### 3.2 补拍策略（`recapture-v1`，业务目录的新字段）

- **可补拍的原因**：上面四个 `quality.target_*`，加上 `quality.blurry`、`quality.exposure`、`analysis.undeterminable`。
- **不补拍**：`target.mismatch`（拍错对象，重拍同一位姿无益）、`model.*`（模型问题不是采集问题）、`analysis.no_reference`、`quality.media_*`（证据完整性问题）。
- **次数**：每次巡检至多补拍 1 次（v1）；由模板按固定次数展开，不是循环。
- **位姿**：只重飞该资产登记的同一观测航线（同位重采）；不生成新位姿、不改航线。使用备选登记拍摄位留到 v2。
- **审批与预算**：补拍任务是一次普通任务，照常编译、准入（含能源预算）、审批、领取与对账；审批页显示「补拍：<原因码>」与原分析作业。时间窗按运行的截止时间，过期即不派。

### 3.3 工作流内核的最小扩展

1. **失败原因可作条件**：谓词新增输出 `recapture`，只对 P4 分析节点有效。节点失败且其拒判原因在业务目录的补拍列表中时为 `true`，否则为 `false`。谓词读取失败节点的原因码，但从不把失败当成完成。
2. **选择节点**：新活动 `select_analysis`（纯确定性，无副作用）按顺序取第一个成功的分析节点作为输出（`analysis_from: [analyze, analyze_recapture]`）。下游复核、发现与工单都引用它，因此现有的复核 / 发现 / 工单语义不变。全部分析都失败时，它以失败结束，原因列出各次拒判。
3. **模板展开示例**：

```text
inspect → await → analyze
                     │ (requires: done, when analyze.recapture == true)
                     └→ inspect_r → await_r → analyze_r
select_analysis(analyze, analyze_r) → human_review → create_work_order …
```

不加循环、不加表达式；DAG 节点上限与校验规则不变。

### 3.4 证据、来源与结算

- 补拍任务的版本来源记 `recapture_of: <原分析作业>`；补拍证据是新的采集，按 D037 / D063 复核后才进入作业。
- 两次都拒判时，运行以未知收尾，原因保留两条，绝不给缺省结论。
- 补拍成功的分析与普通分析一样只是候选。复检结算（`reinspection-v1`）对复检运行里的补拍同样适用：新采集、时序与摘要规则不变。

### 3.5 持久化与入口

- 预计不新增表：策略在业务目录，谓词与选择节点在工作流目录与既有 `wf_nodes.result` 中。实施中如发现需要新列或新表，先按红线提方案。
- 入口不增加补拍按钮：补拍只由模板与策略触发，人只做逐次审批；页面在任务视图显示补拍原因。

## 4. 验证计划

- **S0**（新故障矩阵 P6-F01 起，× 3 种子）：首拍模糊 → 补拍正常 → 复核；两次都被遮挡 → 未知、无缺省结论；`target.mismatch` 不补拍；模型错误不补拍；补拍审批被拒或过期 → 未知；补拍中取消 → 无后继；补拍中服务重启 → 恰好一次补拍；重复事件 → 不重复补拍；跨项目越权。
- **S1**（PX4 SITL）：首飞前用 Gazebo 世界服务在标记上放置遮挡物，首飞后移除，补拍飞行看到完整标记；另一例遮挡不移除，结果为未知。独立裁判核对：补拍次数不超预算、未经审批的飞行 0、缺省结论 0、错误判定 0。
- **指标**：拒判率与人工接管次数相对 P4 模板下降，错误判定不增加；补拍成功率、额外飞行时长与能耗分开报告。
- **回归**：P1–P5 S0 矩阵、P4 / P5 S1 回归、授权矩阵、常驻任务台激活与一次补拍会话。
