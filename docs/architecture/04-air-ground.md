## 1. 协同模型

**一个协调器分配任务，每台机器人维护自己的本地执行与安全闭环。** 协同的单位是任务、空间事实与证据，不是聊天消息，也不是底层运动控制。

| 共享 | 不共享 |
|---|---|
| `MissionPackage` 中的任务节点（含交接规则） | 运动控制、设定值、局部规划器状态 |
| `WorldFact`（场景图增量，带坐标系 / 版本 / 不确定性） | 原始高频传感器流（按需拉取证据片段） |
| `Evidence` 引用与哈希 | — |
| `CapabilityDescriptor` / `RobotStatus` | 恢复策略（各本体自有） |

第一版不要求每台机器人运行大模型；机器人之间不通过自由对话协商动作。研究中「空中提供全局语义、地面执行局部导航与操作」的分工被采纳为默认模式。

## 2. 首个空地端到端场景：巡检—发现—复核—报告

空地扩展的基准场景（近期运营主场景见 [09-operations](09-operations.md)）：

> 无人机完成园区设备巡检，发现疑似外观异常后生成空间标注；地面机器人到达附近进行近距离复核；合并两端证据，分别报告已完成、未完成与不确定的部分。

```text
用户提交巡检目标
    ↓
Coordinator 检查设备能力与可用资源（CapabilityDescriptor + RobotStatus）
    ↓
无人机执行空中巡检（executive/guardian 本地闭环）
    ↓
产出 ObservationRecord：对象 ID · 位置 · 坐标系 · 地图版本 · 时间 · 协方差 · 影像 · 疑似异常（VLM 置信度）
    ↓
Evidence Verifier 确定性检查 → verified；VLM 标记疑似异常 → Coordinator 生成地面复核任务
    ↓
交接协议：offer → 地面机器人确认可达性（自己的地图与底盘约束）→ accept → ack
    ↓
地面机器人近距离重新定位对象（不信任空中坐标的精度）、拍摄、复核
    ↓
证据合并；报告三列：已完成 / 未完成 / 不确定
```

关键约束：**空中看起来有路，不等于底盘可以通过。** 地面机器人必须用自己的局部可通行性判断接受或拒绝任务。

## 3. 四项协同能力（P1/P3 提供通用部分，X1 完成空地语义）

### 3.1 能力发现

- Catalog 维护 `CapabilityDescriptor`（静态）与 `RobotStatus`（动态，1 Hz）。
- 分配条件同时考虑静态能力与当前能源、载荷、定位与通信状态。
- 缺能力 → 调整计划或明确拒绝；不做假接口。

### 3.2 空间对齐

- 每个 `WorldFact` 带 `frame_id`、`map_version`、协方差；跨机器人传递前经 `SpatialAlignment` 服务转换到接收方坐标系，并合成不确定性。
- 对齐质量低于阈值时，**不交付一个看似精确的目标点**，改为交付「搜索区域 + 语义描述」，由接收方自行重新定位。
- 坐标约定：全局 WGS84 + 本地 ENU（原点带版本）；姿态 ENU/FLU；海拔参考显式（AMSL / AGL / 相对起飞点）；时间统一 UTC，机器人间时钟偏差进入不确定性。

### 3.3 任务所有权与交接

交接协议（事件均进入 `ExecutionEvent`）：

```text
handoff_offered(task, from, to, expires_at)
  → to 评估可达性与资源 → handoff_accepted | handoff_rejected(reason)
  → from 确认 → 所有权转移；租约在 to 侧签发（新 lease_epoch）
  → handoff_completed | handoff_timeout（回到 Coordinator 重新分配）
```

规则：任一时刻一个任务只有一个逻辑所有者；accepted 只是愿意接收，不转移所有权。超时或 ACK 丢失先对账，无法证明原执行者已释放时保持物理占用；不能直接重分配冲突任务。接收者的 assignment_epoch 与本机 TaskLease.lease_epoch 分别校验（租约过期不等于物理停止）。

### 3.4 时空资源预约

- 共享资源：降落区、狭窄通道、观察位置、充电 / Dock 位。
- 预约对象：`{resource_id, holder, time_window, spatial_bound}`；由 Coordinator 仲裁。
- 机器人失联时，其预约保留一个保守边界（最后位置 + 最大速度 × 失联时长 的包络），直到状态对账完成。

## 4. 一致性策略：控制权与地图事实不同

| 对象 | 一致性 | 机制 |
|---|---|---|
| 跨机器人任务所有权（目标设计） | 强一致、单写者 | Coordinator 仲裁任务分配与交接；接收方按授权建立本地 `TaskLease`，guardian 校验 `lease_epoch` 并拒绝旧指令 |
| 地图与观测事实 | 最终一致、允许迟到 | 带时间戳与版本的增量合并；冲突以更新且不确定性更小者为准，保留历史 |
| 任务账本（云端） | 可暂时不可用 | 机载本地权威状态 + 事后同步 |

## 5. 通信形态

- 每台机器人独立 ROS 2 域；跨机器人只走 Zenoh 路由或车队协议（protobuf/JSON Schema），不让 DDS 发现跨无线链路。
- 车队协议是传输无关的：Zenoh（ROS 2 机器人）、MQTT（DJI Cloud API 类平台 / Dock）、gRPC（服务间）。
- 带宽受限时传场景图增量与证据引用，不传原始流。

## 6. 现有具身项目的位置

`embodied-agent` 当前落地的是桌面操作机械臂；真正的地面移动协同需要移动底盘适配、定位地图与导航技能。地面导航采用 Nav2 适配器（行为树、规划器 / 控制器插件、恢复行为、导航 action 接口），本项目的 agent 只负责任务语义与协同。二维地面导航能力不等同于三维避障能力，两者不共用局部规划器。

## 7. 仿真中的空地联合

X1（原 M4-B）联合仿真优先在**同一个 Gazebo 世界**里用 PX4 SITL 同时运行多旋翼与 rover（PX4 v1.17 提供 rover 模式与 Ackermann SIH），避免早期对接两个仿真器并处理时空同步。Nav2 仿真适配保留原 WP-M4B-10，归 X1 后续，可与 H3 地面平台准备衔接，必须在真实地面平台前完成（WP-M4B-10）。
