# 运营解释助手（WP-P6-05，D083）

操作者问「这个任务为什么被拒、还缺什么证据、和上一版有什么不同」时，助手只依据服务给出的事实表回答，并逐条引用事实。服务核对每一处引用，核对不通过就只展示确定性的摘要。助手只读，没有工具，不产生任何版本。

## 1. 要解决的问题

一个任务被拒、被拦、待补证或没有完成时，原因分散在多处：版本状态、规划结果（拒答原因）、准入的问题码、派遣判定、审批与有效期、各步骤的执行 / 效果 / 安全判定、证据核验与报告。D080–D082 又加了拒答原因和 `scope.foreign_reference` 等码。操作者要自己把它们拼起来。

外部评审建议（[评审记录](research/external-review-2026-10-10.md)）：第一版只做状态解释与证据追问，只读、引用原因码与缺失证据；任务修改只生成差异草案，并重新审批。验收要求是：

- 不编造原因；
- 不沿用旧审批；
- 模型没有新增工具权限。

## 2. 设计

### 2.1 事实表（确定性）

服务按调用方的读权限，从任务视图生成事实表。每条事实有稳定 id、类型与内容，全部取自已有记录，不调用模型：

| 类型 | id 形如 | 内容 |
|---|---|---|
| 任务 | `mission` | 状态、当前版本、请求文字、所选体积与资产、绑定（项目、站点、机器人） |
| 版本 | `version:2` | 状态、来源（规划、重规划、补拍等）、目标资产、与上一版的包差异 |
| 规划 | `planner:2` | 结果（planned / refused / failed）、拒答原因、模型与提示版本 |
| 问题 | `issue:<序号>` | 问题码、层、说明、涉及对象 |
| 准入 | `admission:2` | 是否通过、问题码、能源上限 |
| 审批 | `approval:2` | 是否已批准、批准时间与到期时间、签名键（不含登录名） |
| 步骤 | `step:2:<task_id>` | 执行状态、效果判定、安全判定 |
| 证据 | `evidence:<id>` | 所属版本与步骤、核验结论 |
| 缺失 | `missing:<种类>:<对象>` | 确定性推出的缺口，见下 |
| 报告 | `report` | 报告中的「已完成」只接受 `succeeded ∧ verified` |

**缺失证据**由服务确定性推出：

- 有步骤的效果判定不是 `verified`；
- 有依赖步骤因前序未核验而没有放行；
- 有采集的核验结论不是通过；
- 版本还在等审批，或审批已过期（包括到期后不能沿用旧审批）；
- 任务已被拒绝、规划拒答或失败，因而没有可执行的版本。

### 2.2 模型回答（只读、无工具）

- **输入**：系统提示 `explain-v1`、事实表（JSON，按数据处理，不作为指令）和操作者的问题。
- **输出**：一次函数调用 `submit_explanation`，字段如下：
  - `answer`：不超过 800 字；
  - `citations`：至少一个事实 id；
  - `missing`：缺失事实的 id；
  - `change_draft`：只在操作者想改任务时给出，是一段新的请求文字，服务不会执行它。
- **没有工具**：模型没有任何工具，事实表由服务按调用方权限生成。规划器的模型身份与 provider 照旧共用（D029），实调交互与规划一样录制。

### 2.3 确定性校验

模型的回答只有通过全部校验才展示：

1. `citations` 与 `missing` 中的 id 都存在于事实表，且 `missing` 只能引用缺失类事实；
2. `answer` 中出现的问题码（形如 `scope.foreign_reference`）、证据 id、步骤 id、版本号都在事实表中；
3. 断言类措辞要有事实支撑：
   - 说「已批准」须有当前版本的审批事实；
   - 说「已完成」须有 `succeeded ∧ verified`；
   - 说「可以沿用旧审批」一律不通过。

不通过时不展示模型文字，改为展示由事实表按模板生成的确定性摘要，并写明「模型回答未通过校验」及第一条原因。

**差异草案**：`change_draft` 只是文字草案。页面提供「填入提交框」，操作者照常提交后，走正常的规划、准入与逐次审批（D032），服务不会因为解释产生任何版本。

### 2.4 接口与页面

- **接口**：`missions.explain`，scope 为 MISSION_READ，参数 `mission_id`、`question`。按调用方的项目角色检查读权限，返回以下内容，不存储：
  - `facts`；
  - `explanation`（通过校验时）；
  - `validation`；
  - `summary`（确定性摘要）；
  - 模型与提示版本。
- **页面**：任务详情里加「解释」区：
  - 输入问题后显示回答，引用以标签形式列出，点击可定位到对应事实；
  - 校验失败时显示确定性摘要；
  - 差异草案可一键填入提交框。
- **不变的部分**：不新增控制帧、不新增表、不改权限表。

## 3. 评测（预先写定）

- **语料** `explain_v1`：由 `scripts/build_explain_corpus.py` 一次性生成，冻结 12 个任务状态的服务视图（只保留事实表读取的字段，不含登录名），逐个固定摘要。状态来自三处：
  - 任务台目录上的规划路径：跨站点拒绝、规划拒答、未登记体积、能源拦截、越出所选范围、待审批、审批人驳回；
  - 闭环 harness：首飞证据未核验后由策略重规划的第 2 版，以及之后完成的同一任务；
  - P1 S0：领取前机场舱盖卡住后取消、审批与领取之间进入维护后取消、领取前审批过期。

  每个状态配中英文问题各一，另有两个状态配修改请求，共 26 例。每例写明决定性事实，即回答应当引用的事实。
- **替身**：伪造引用、编造问题码、声称已批准或可沿用旧审批、遗漏决定性原因。判据：校验必须全部拦下，通过校验的伪造为 0。
- **实调**：MiniMax-M3 + `explain-v1` 录制一次，严格回放。
  - 判据：展示给操作者的回答中编造为 0，这由校验保证、由回放复现。
  - 只报告、不设阈值：模型原始回答的校验通过率、原始编造率、决定性原因的引用率。
- **任务台**：激活后，经入口提交一条点名别处的请求（被 `scope.foreign_reference` 拒绝），再就它提问。两种结果都算端到端正确：通过核对的回答引用了事实，或者回答未通过核对、展示的摘要写出了这个问题码。模型回答的质量由语料实调衡量，不由这一次入口核对衡量。

## 4. 门禁 `scripts/verify_explain.py`

| 判据 | 内容 |
|---|---|
| `scope` | 改动只在解释模块、服务读接口、控制台页面、提示、评测、脚本、测试与文档；不涉及机载 |
| `checks` | 候选上的云端检查通过（含客户端测试之外的全量 pytest） |
| `doubles` | 当场运行：替身的伪造全部被校验拦下 |
| `live` / `replay` | 实调录制在候选上严格回放，逐例复现；展示的回答中编造为 0 |
| `regression` | 当场运行 P1 S0 与授权矩阵，以及页面客户端测试 |
| `desk` | 激活、页面与健康、伪造身份；经入口的解释回答通过校验并引用决定性问题码 |
| `historical` | 先前的发布记录不变 |

## 5. 边界

- 解释不改变任何状态，不产生版本，不触达执行。模型没有工具，看到的事实表按调用方权限生成。
- 第一版只覆盖任务（mission）。工作流运行、调度任务单、发现与工单留待后续。
- 校验只能拦下可核对的编造（引用、问题码、id、断言措辞）。表述是否恰当、是否抓住重点仍要由人判断，这部分评测只报告引用率。
