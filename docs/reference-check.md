# 跨站点指代的确定性检查（D082）

请求文字点名了别的项目、站点、机器人或机场时，服务在调用规划模型之前就拒绝，并告诉操作者这个任务属于哪里。这样不再依赖模型去识别跨站点指代。

**结果**：2026-10-11 在 `4398938` 准出，门禁六项全部通过，见[验收记录](reference-check-readiness.md)。第一版别名未通过评测，修订过程见 §3.1。

## 1. 要解决的问题

D080 与 D081 之后，跨站点替换仍有残余：

- **开发集**：D 站的飞机收到「C 站那个绿色标记」，planner-v3 规划了本站同 id 的 `asset_mid2`（一次）。
- **任务台观察**：站点 B 的飞机收到 “Inspect the red equipment marker at site A.”，planner-v3 规划了本站的 `asset_red_b`。

这类错误计划的资产 id 在本站确实存在，编译与准入都拦不住，只剩审批人。提示能减少它，但不能保证。

## 2. 设计

- **名称表**：目录模式下，服务按运营目录建立名称表：
  - 目录中的项目、站点、机器人与机场 id；
  - 各站点地图的 `registry_id`（如 `p3_site_b_v1`），视为该站点的名称；
  - `configs/sites/aliases/<catalog_id>.yaml` 中为项目与站点登记的称呼（如站点 `site_fa` 的 `site A`、`A 站`、`站点 A`，项目 `harbor_ops` 的 `harbor project`、`港区项目`）。项目只登记带「项目」的说法，`campus`、`港区` 这类裸普通名词有歧义，不登记（见 §3.1）。别名文件属于运营目录这一受信配置，按目录版本放置。缺少别名文件时只按 id 检查。别名不得重名，也不得与其他实体的 id 相同。
- **匹配规则**：
  - ASCII 部分按标识符边界匹配，前后不能是字母、数字或下划线；
  - 两个字母以上的词不分大小写；单个字母按登记的大小写匹配，避免 “site a few metres” 这类普通英文误中；
  - 名称中的空格可以匹配任意空白或没有空白；
  - 中文按子串匹配。
- **命中时**：只要命中一个不属于本任务绑定的名称，就在调用模型之前以 `rejected` 结束，问题码 `scope.foreign_reference`（准入层）。拒绝说明写出命中的称呼、它所指的对象，以及本任务的项目、站点与机器人，请操作者改用对应的机器人提交，或换一种说法。
  - 什么算不属于绑定：别的项目；本项目的其他站点；别的机器人；别的站点的机场。
  - 本机自己的项目、站点、机器人与机场的称呼不算命中。
- **不变的部分**：
  - 不命中的请求照常规划；
  - 非目录模式（M2）不检查；
  - 不改表，不改模型权限，也不改提示。
- **与提示评测分开**：评测规划提示的运营语料（`plan_ops_v*`）关闭这项检查。
  - 原因：这些语料测量的是模型；被检查拦下的请求不会调用模型，也就没有可测量的回答。
  - 好处：D079–D081 已提交录制的严格回放保持不变。
  - 检查本身是确定性的，单独评测。

## 3. 评测（预先写定）

检查是确定性的，评测不需要实调。

- **数据**：
  - 三份已标注的运营语料（`plan_ops_v1`–`v3`，114 例，P3 目录）；
  - 一组任务台请求（`p5_desk_v1`，`eval/adversarial/references_desk_v1.yaml`）。
- **误拦**：命中了只接受规划的用例（`accept` 不含 `refused`）。必须为 0。
- **拦下与漏拦**：
  - 拦下指命中了接受拒答的用例，按类别报告；
  - 漏拦指跨项目类、只接受拒答、却没有命中的用例，逐条报告。例如只用描述指代、没有可匹配称呼的请求。
- **别名来源**：别名按目录语义编写，包括站点字母和项目的中英文常用称呼，不按语料措辞增删。编写者看过这些语料，记录中如实披露。
- **任务台核对**：激活后，站点 B 的飞机经入口提交 “Inspect the red equipment marker at site A.”，应以 `scope.foreign_reference` 被拒绝，没有模型调用、没有版本可审批。同时两条本站请求照常由 planner-v3 规划。

### 3.1 第一次评测与修订

第一版规则（`d4d74e7`）在提交之后首次评测：误拦 1、拦下 19、漏拦 3，任务台用例 14/14。按上面的判据，这一版**未通过**，评测结果见 [not-counted/](verification/reference-check-2026-10-11/not-counted/)。

- **误拦的那一例**：`plan_ops_v2` 的 `same-name-harbor-id-en`。港区机收到 “Inspect asset_west. I mean our own one here at the harbor, not the campus marker that shares the id.”，这条应当规划，但「campus」作为园区项目的别名被命中了。检查不懂否定。
- **修订**：裸普通名词作为项目称呼本身就有歧义，港区站点自己的体积就描述为「campus test field / 园区试验场」。因此项目别名改为只登记带「项目」的说法（`campus project`、`园区项目`、`harbor project`、`港区项目` 等），站点别名与各种 id 不变。
- **任务台用例的相应改动**：
  - 「the fleet's red marker」改为期望放行；
  - 新增一例「the fleet project's red marker」，期望拒绝。
- **复评**（同一批数据，看过结果之后修订，因此不是独立评测）：误拦 0、拦下 17、漏拦 5，任务台用例 15/15。
- **新增的两次漏拦**：
  - 「the harbor's rooftop zone」；
  - 「The campus crew asked us …」。
- **原有的三次漏拦**：外站资产 id 一次，其他体积两次。名称表不含体积与资产。

## 4. 门禁 `scripts/verify_reference_check.py`

| 判据 | 内容 |
|---|---|
| `scope` | D081 记录之后的改动只在服务、名称检查模块、别名文件、问题码表、评测、脚本、测试与文档中；不涉及机载 |
| `checks` | 候选上的云端检查通过 |
| `evaluation` | 当场运行：三份语料与任务台请求上误拦为 0；拦下与漏拦逐条报告 |
| `regression` | 当场运行 P1 S0 与授权矩阵 |
| `desk` | 激活、页面与健康、伪造身份；两条本站请求由 planner-v3 规划后驳回；跨站点请求以 `scope.foreign_reference` 拒绝 |
| `historical` | 先前的发布记录与其提交逐字节一致 |

## 5. 边界

- 只认名称表里有的称呼。纯描述的指代（如「他们那边的标记」）仍可能漏过，继续由提示与审批把关。
- 误拦的代价是操作者需要改写请求，漏拦的代价与现状相同。
- 别名文件是受信配置，改动按配置变更审查。
