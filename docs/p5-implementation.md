# P5 详细方案：无硬件平台 v0.1

[总任务表](operations-implementation.md) · [运营架构](architecture/09-operations.md) · [路线图](roadmap.md) · [任务台指南](tailnet-desk.md)

**状态：2026-10-02 设计；2026-10-05 候选 `4c3de14` 门禁未通过（72 h 长稳的恢复判据），按 D073 修复后以新候选重跑，见 [P5 记录](p5-readiness.md)。** P5 把已验证的 P1–P4 能力集成为一个可持续运行的无硬件平台：常驻任务台（`8448`）就是平台 v0.1 的唯一入口。交付五项：五工作区与项目审计（WP-P5-01）、第二业务模板（WP-P5-02）、厂商协议合同测试（WP-P5-03）、72 小时真实墙钟长稳（WP-P5-04）、版本交付与运维文档（WP-P5-05）。P5 不新增数据库表（见 §2）；机载 executive / guardian / 适配器 / uplink、wire、技能、平台与恢复策略不改。

## 1. 验收场景与范围

- **平台部署**：常驻任务台的同一个任务服务同时服务三个项目：`campus_s1`（PX4 SITL 上的 `uav_01`，S1）、`fleet_s0`（两台逻辑 UAV 与两个逻辑机场，S0）、`vendor_s3`（一个厂商托管机场的协议模拟器，S3）。每台机器人的执行后端由运营目录声明，服务只接受部署允许的后端集合，`real_device` 一律拒绝（D069）。
- **一入口走完整主场景**：在任务台页面中启动 `appearance_watch`，逐个审批飞行、复核发现、建单、记录维修反馈、审批复检飞行、复核本轮，直到工单关闭、发现解决；随后在「运行审计」工作区看到这条链路的全部人工与系统动作。损伤与修复是 Gazebo 世界的变化，由编排在入口之外放置与移除，入口没有任何世界或飞控接口（D070）。
- **第二业务模板**：园区道路障碍候选复核（`road_watch` / `road_reinspection`）：道路段登记标线上出现障碍 → 候选发现 → 人工复核 → 清障工单 → 清障反馈 → 复检关单；由外部「道路报告」事件或人工启动。只加目录、站点地图与仿真世界，不改通用工作流内核与业务层代码；任务、数据与验收范围单独冻结（D071）。
- **厂商协议合同**：自有 PX4 之外的第二条执行路径。厂商托管机场经 `VendorMissionGateway` 接收已审批的高层任务；S3 模拟器实现固定版本的协议档案，注入重复、乱序、丢 ACK、断线重连、取消与证据缺失。ACK 只表示受理，结果以进度终态与服务复核过的证据为准；不开放任何低层控制；不宣称兼容任何真实固件（D072）。
- **72 小时长稳**：在平台部署上按真实墙钟排班运行：S0 持续逻辑负载、S1 与 S3 间歇飞行、S2 间歇实调探针；期间注入服务重启、上行断网、模型不可用与限流、积压、取消与越权探测，并持续记录资源。计划触发与实际完成逐条对账（D073）。
- **边界**：没有真实设备；S0 逻辑飞行、S1 单架 PX4 SITL、S3 协议模拟、S2 的 VisA 素材分别计数，不互相代替。P4 的 S2 精确率仍未达冻结要求，P5 不宣称任何模型精度（D069）。工单仍是账本中的模拟工单。

## 3. 语义要点

### 3.1 依赖与准出口径（D069）

P4 门禁十五项中十四项通过，只有 S2 精确率未达冻结要求（0.8835 < 0.90），按用户决定保持开放。P5 依赖的是 P4 的业务闭环（质量层、分析作业、发现、复核、工单轮次、复检结算、数据复用），这些已在 S0 / S1 / 常驻任务台通过；P5 门禁读取 P4 的机器门禁，要求除 s2 外全部通过，并把 s2 原样列为开放项。P5 的任何结论都不涉及模型精度，S2 的后续仍按 D065 / D066。这与 P 线只消费 M3-SITL 子结论、JIL 单列为 missing 的做法一致。

### 3.2 平台部署与每机执行后端（D069）

- 运营目录中每台机器人声明执行后端；服务的 `--execution-backend` 是本部署允许的集合（如 `px4_sitl,logical_sim,vendor_protocol_sim`），目录中出现集合外的后端即拒绝启动。`real_device` 不在任何允许集合中。
- 每个后端一个受信 `SourceContext`（同一次运行 ID、软件 SHA 与平台摘要）；任务版本的来源按其机器人的后端写入，客户端仍不能提供或改写后端。领取闸门继续核对版本来源的后端与机器人目录后端一致。
- 常驻任务台的 S0 机队（`desk-fleet`）是独立容器：真实 uplink / guardian / executive 加逻辑飞行适配器，经 mTLS gRPC 连接任务服务，每台各有证书；它的逻辑机场以绑定的 `dock:` 身份经 API 套接字报告。S3 模拟器（`desk-vendor`）同样是独立容器，只经一个私有套接字与网关通信。服务从不读取模拟器的真值或故障开关。
- S0 / S3 环境不挂真实设备、真实证书或生产队列：任务台本身只有仿真，证书是任务台自己的测试信任根。

### 3.3 项目审计与授权矩阵（D070）

- `audit.list(project_id, before, limit)` 返回一个项目按时间倒序的审计条目：提交（请求者、通道、原文前 160 字）、审批与驳回（审批人、任务包哈希）、操作请求（暂停 / 恢复 / 取消）、工作流的启动 / 取消 / 排班启停 / 复核 / 维修反馈 / 草案、调度任务单与分配、发现复核、工单与轮次、参考外观、复用分析、机场维护锁与动作、领取 / 作废 / 释放，以及项目成员的越权尝试（`access.denied`）。每条带时间、身份、动作、对象与来源表。机场的逐次状态报告不列入（另有资源视图）。
- 条目只来自既有表，按对象归属映射到项目；不可读的项目一律 `service.not_found`。查询只扫最近的审计行并按索引取回对象，开销与历史总量无关。
- 授权矩阵（`eval/p5_authz.py`）对 API 的每个方法、hri.v0 的每种上行帧、媒体读取与订阅推送，分别以非成员、他项目成员、viewer / operator / approver / reviewer / admin、A2A、匿名、机场与事件后端身份调用，核对结果与按 scope 表推导的期望一致：非成员看到 `service.not_found` 且应答中没有对象数据，角色不足为 `auth.project_denied`，第三方与后端只能调用各自的方法。逃逸计数必须为 0。

### 3.4 一入口主场景（D070）

- 任务台的工作流目录逐字节保留 P4 模板；`appearance_watch` / `appearance_reinspection` 使用颜色特征插件，可以关单。任务台世界默认没有损伤，因此主场景需要世界变化：`dev_stack.py desk-world` 经 SSH 把资产外观写入 `desk/world/appearance.json`（损伤 / 正常 / 障碍），监管者在每架次仿真器就绪、guardian 启动之前按它放置或不放置模型，并把每次放置写入该架次的记录。
- `desk_browser.py --loop appearance_watch --loop-asset asset_blue --repair --world asset_blue` 在真实浏览器中走完（不用 `asset_red`：任务台上它仍有一张按 P4 设计不能关单的任务台工单，见 D073 补记）：开始前经 `dev_stack.py desk-world` 放置损伤；启动运行 → 审批巡检 → 发现 → 复核确认 → 建单 → 维修反馈（同一时刻经 `desk-world` 移除损伤）→ 审批复检 → 在运行详情中确认本轮复核 → 结算 `passed` → 工单关闭、发现解决；最后打开「运行审计」，读回这条链路的条目（门禁要求其中有操作者本人的审批、发现复核与维修反馈）。

### 3.5 第二业务模板：园区道路障碍候选复核（D071）

冻结范围：
- **任务**：道路段登记标线上是否有障碍物遮挡；候选只送人工复核，由 reviewer 确认后建清障工单；清障反馈之后的新采集未见障碍且本轮确认才关单（`reinspection-v1` 原样适用）。
- **资产与世界**：S1 / 任务台为 `road_north`：M2 世界中 (2, 8) 处 4 m × 2 m 的绿色道路段标线（`sim/p5_setup.py` 写入 P5 仿真镜像；M1 / M2 镜像与世界不变）；障碍物是 1.6 m × 2.0 m 的暗色箱体，遮住标线约 40%。S0 为 P5 站点地图中的 `road_a` / `road_b`，障碍在逻辑相机中渲染为覆盖标线的块。
- **分析**：确定性颜色特征插件，在 S1 渲染上标定无障碍时的绿色占比区间；S0 用 S0 渲染的区间；任务台另以冻结的 change-v3 实调给出并列候选（不参与关单）。没有授权的道路实拍素材，因此**不做 S2、不宣称任何障碍识别精度**；发现按既有 `appearance` 缺陷族聚合（障碍属于其中的 `foreign_object` / `other_change`）。
- **触发**：人工、道路报告事件（`event:road-reports`，`road.report`，载荷只能选择已登记的道路段）与默认停用的间隔排班；同一事件重复投递只启动一个运行。
- **验收**：S0 矩阵 P5-R01–R08 × 3 种子；S1 三个用例（关单 × 种子 7 / 19 / 41）加一个未清障轮次；门禁核对 P5 候选相对 P4 候选没有改动通用工作流内核与业务层文件。

### 3.6 厂商任务网关与 S3 合同（D072）

- **协议档案** `configs/vendors/dock_task_v1.yaml`（`drone.vendor-profile/v1`）：协议名与版本、任务类型（只有航点巡检）、四个命令（`flighttask_prepare`、`flighttask_execute`、起飞前取消 `flighttask_undo`、飞行中取消 `return_home`）、ACK 语义（只表示受理）、事件（进度、媒体回调、返航信息、机场状态）、命令去重窗口、重连后是否重放最近进度、可见性（遥测：位置、电量、模式、舱盖、在位；日志与安全事件不可见）、安全责任（厂商本地：避障、返航、地理围栏、电池保护）、载荷、跨机场能力（无）、低层控制（`none`）。结构参照公开的机场云接口任务流程，字段名是本项目自定；档案明确 `verified_against_firmware: false`。加载时拒绝声明低层控制或白名单之外命令的档案。
- **编译与授权**：厂商任务与自有 PX4 任务一样经编译、准入与逐次人工审批；审批签名仍绑定任务包哈希。厂商任务（航点、拍照动作、起降机场）由任务包确定性推导，推导器版本与档案摘要一起写入版本的 `vendor_task` 命名空间，审批时页面同时显示其摘要；网关在领取时验签、重新推导并核对摘要，不一致即拒收。
- **领取与执行**：网关在服务进程内经同一领取闸门拉取投递（取消意图、审批有效期、来源后端、预约与可派遣判定都在事务内重查），然后发送准备与执行命令；每个命令的事务 ID 由任务、版本与命令确定，重发沿用同一 ID，因此丢 ACK 或重启后的重发不会产生第二次执行。厂商机场状态由网关转成 P1 机场报告、以绑定的 `dock:` 身份入账；厂商飞行器状态转成机器人状态。
- **对账**：进度事件按厂商序号只前进不后退，终态不可被迟到的非终态覆盖；重复事件只入账一次；断线期间机场链路为未知，重连后按档案重放的最近进度对账；终态未知时任务保持未完成且预约不释放。
- **结果与报告**：巡检步骤完成 = 厂商报告到达拍照之后 ∧ 服务复核厂商上传的媒体为 `verified`；没有媒体、摘要不符或复核未过都不完成。起降等步骤的效果对平台不可见，记 `unknown`；安全判定记 `unknown`（厂商责任）。报告「已完成」仍只接受 `succeeded ∧ verified`。厂商任务不自动重飞。
- **取消**：取消意图先持久化；未领取即作废；已领取未执行发 `flighttask_undo`；执行中发 `return_home`；ACK 只是受理，进度 `canceled` 与机场在位证据齐备才算收尾，否则显示取消中。
- **释放**：厂商终态之后的地面状态与机场新鲜在位报告齐备，P1 对账才释放预约。

### 3.7 72 小时长稳（D073）

- **计划**：`configs/soak/p5_soak_v1.yaml` 固定排班、故障与探测的节奏和随机种子，长稳开始时与候选 SHA、部署 ID 一起写入 `desk/soak/<长稳ID>/manifest.json`；开始时刻 T0 只存在于这个文件，服务重启不影响它。
- **负载**：S0 每 15 分钟一次 `fleet_watch`（两台逻辑 UAV 交替），每 3 小时一次损伤 → 修复循环；S1 每 3 小时一次 `appearance_watch`（红 / 蓝交替），每天一次损伤循环（`asset_blue`）与一次 `road_watch` 障碍循环；S3 每 30 分钟一次 `vendor_watch`，协议故障按计划穿插；S2 每 6 小时用冻结的 change-v3 实调 8 张 VisA 校准拆分图（不用测试拆分，不计入任何指标）；每天一次 15 个运行的积压突发；约 5% 的 S0 运行在随机阶段取消；每 30 分钟一组越权探测；每 2 小时一次自然语言实调规划提交。
- **编排身份**：审批、复核、维修反馈与取消由主机上的长稳编排（`scripts/desk_soak.py`，systemd unit）以 `harness:soak-*` 身份经 API 完成（成员列表是受信部署输入），全部计为编排介入；真人操作单独记录。复核按世界真值决定（巡检运行：世界有损伤 / 障碍才确认；复检运行：世界已恢复才确认）。PX4 任务只在项目仿真锁空闲时审批，因此长稳期间可以照常运行其他云端批次，S1 只会延后。编排自身重启时按日志续跑：请求号按发生时刻固定，不会重复启动；它停机期间错过的发生时刻记为 `missed`（编排原因）。
- **故障**（整容器，经 Docker 或只由编排写入的开关文件；强杀是主机对容器主进程发送 SIGKILL，由 `unless-stopped` 重启，与崩溃相同）：服务每 8 小时一次正常重启、每天一次强杀；S0 机队上行每 6 小时断网 5 分钟、S1 上行每天一次断网 3 分钟；厂商链路每 6 小时断开一次；模型端点每 12 小时各一次 15 分钟不可达（断开代理出站网络）与 15 分钟限流（代理对 CONNECT 回 429，开关文件只由编排写入）；逻辑机场与机队容器每天重启一次。
- **采样**：每 60 秒记录各容器 CPU / 内存 / 重启次数、主机负载 / 内存 / 磁盘、账本与媒体体积、各表行数、待审批 / 活动运行 / 作业队列长度与 API 往返时延。
- **判据（运行前冻结）**：
  1. 同一部署持续 ≥ 72 h；服务可重启，账本从未重置（只追加的表行数单调不减，T0 之前的记录仍在）。
  2. 每个计划发生时刻都有且只有一个结果：启动的运行，或因服务停机落在启动窗之外而记为错过；无法由停机解释的错过与重复启动均为 0。
  3. 每个运行在结束时已终结，或仍在活动且有可解释的等待原因；丢失运行为 0。
  4. 计数为 0：未知算成功、取消后新派飞、重复派飞、权限越界、错误关单、重复发现 / 工单、厂商重复执行、ACK 当完成。
  5. 每次故障后系统自行恢复：服务 2 分钟内就绪、机场会话 1 分钟内恢复活动、此后的计划运行按时启动；模型故障窗口内的分析与规划以带原因的拒判 / 失败结束，窗口后恢复成功。
  6. 资源：除注入外没有容器被杀或重启，内存不越过限额，积压在突发后 6 小时内排空，磁盘与账本增长率记录在案。
  7. 分层计数：S0 / S1 / S2 / S3 的计划、执行、成功、失败、未知、取消、作废分别报告；S1 至少 12 次飞行完成，S3 至少 100 个厂商任务，S2 至少 10 次探针。
- **缺陷**：长稳中出现阻断缺陷时停止计时，修复后以新候选重新开始 72 h，旧记录保留为负记录。
