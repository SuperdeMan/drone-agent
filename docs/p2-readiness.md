## 已实现范围

- **模板与校验**（WP-P2-01，D057）：`drone.workflow-catalog/v1` 只含 8 种白名单活动，参数有类型并拒绝未知字段；条件只有对 `suspected` / `decision` 的相等谓词。图无环，至多 40 个节点、10 个任务；工单必须以复核确认为条件，复检不链式触发。加载时按运营目录与站点登记表核对机器人、体积与资产，运行固定目录与模板摘要。
- **存储与内核**（WP-P2-02，D058 已批准）：同一账本新增 9 张 `wf_` 表与 5 个索引，`schema_version` 仍为 2（另记 `meta.workflow_schema=1`），P1 版本可直接在迁移后的库上启动。引擎按运行持有 10 s 租约，接管时 fencing 代次加一；节点推进为带 `state_version` 的 CAS，外部效果与 outbox 行同事务写入，消费者按唯一键去重。
- **触发**（WP-P2-03）：人工、每日 / 间隔排班、绑定的 `event:` 身份与内部复检四类，去重键为（项目、流程、版本、来源、事件 ID）。排班只启动启动窗内最近一次，错过的只记录；时区取固定版本 tzdata。
- **任务桥接**（WP-P2-04）：`service.submit_workflow` 以 `workflow:<run_id>` 和活动键提交普通任务，经同一编译、准入与软预约；每个任务仍逐个人工审批。`await_mission` 只在任务终态、预约经对账释放且证据经服务复核后完成。
- **取消**（WP-P2-05）：取消代次、作废未领取 outbox 与 P1 任务取消意图在同一事务写入；领取守卫在任务服务事务内复核，取消后不再开始新节点；子任务对账释放前运行保持 `cancelling`，迟到的成功只记录。
- **业务活动**（WP-P2-06）：脚本夹具 / 确定性颜色特征分析（结果同时密封进任务版本来源）、reviewer 复核、按幂等键的模拟工单、维修反馈与复检运行。
- **入口与草案**（WP-P2-07）：`workflows.*` API、任务台工作流面板与 hri.v0 帧；草案由模型只填窄意图、代码编译校验，只返回不保存，没有激活接口。
- **验证底座**（WP-P2-08）：S0 世界与 P2-F01–F15、S0 / S1 独立裁判（含反向验证）、云端 S1 执行器、工作流草案对抗语料与门禁。

机载 executive、guardian、适配器、wire、技能与恢复策略均未改动，门禁的 scope 判据据此确认不需要重跑 M1 飞行矩阵。P1 的机场收尾（D057 §10）有一处修正，因此门禁当场重跑 P1 S0 矩阵。

## 故障矩阵与 S1

S0 的 15 类故障（每类 × 种子 7 / 19 / 41）都由独立裁判在线与按录制各判一次，两次结论一致。裁判在每一例都核对以下不变量：
- 每个逻辑活动至多一个任务；
- 取消提交后不新建、领取或开始任何东西；
- 没有证实巡检的运行不算完成；
- 没有 reviewer 确认不建工单；
- 每个触发键一个运行；
- 不越出项目。

下表是各例在这些不变量之外的实际判定：

|---|---|---|
| F01 | `campus_round`：同一机器人依次巡检两处标记，红色疑似并被确认 | 2 次飞行、2 次分析、1 次复核、1 张工单；第二个任务在第一个任务对账释放后才提交；运行完成 |

## 常驻任务台迁移与会话

迁移前的常驻账本是 P1 迁移后的 schema v2 数据：31 个任务、33 个版本、1143 个事件，P1 运营表中另有 12865 条审计事件。

迁移在首个候选 `373e0a8` 激活时完成，迁移代码与最终候选相同：
1. 先在副本上依次演练 D056 与 D058。P1 部分为 `current`，P2 部分为 `migrated`，`integrity_check=ok`，新增 9 张 `wf_` 表；工作流以外的全部转储摘要迁移前后相同（`b470a8547eb2e85b…`）。
2. 演练通过后才迁移正式账本。迁移前备份 `ledger-v2-20260926T043816364350Z.sqlite3`（sha256 `b07b86891bdd5d9d…`，逐表行数与迁移前一致）与 P1 的 v1 备份一同保留在云端状态目录。

最终候选 `3bdbd50` 激活时，副本演练与服务启动都报告两部分为 `current`。回退路径保持 D058：`schema_version` 仍为 2，可直接部署 P1 版本（它不读 `wf_` 表），或停服恢复备份。

最终候选的入口验证都经真实 Tailnet HTTPS 进行，探针回执已脱敏：
- **HTTP**：页面 200，脚本与本检出一致；健康检查中页面、任务服务与 M1 运行时都是 `3bdbd50`，规划器为 MiniMax-M3 实调。
- **工作流入口**：调用方在 `campus_s1` 的角色为 operator / approver / reviewer / admin；目录 `p2_s1_v1` 的三个模板齐全，每日排班停用。MiniMax-M3 实调草案（请求为「每天早上9点（北京时间）巡检红色设备标记；分析疑似异常并经人工复核确认后，创建维修工单。」）为 `planned`、`active: false`，只用项目机器人 `uav_01`，节点为提交任务 → 等待 → 分析 → 人工复核 → 模拟工单 → 报告。注入、机场报告、解锁、飞行、模拟器注入、草案激活与批量审批 7 种帧都以 `unknown type` 被拒。
- **工作流会话**（约 216 s）：以页面方式启动 `asset_check`（红色）。
  1. 巡检任务 `m-ff4ecdae7e95` 经审批和领取闸门交付，监管者飞行后以 `reconciled` 释放。
  2. 脚本分析给出疑似，reviewer 确认后建模拟工单。
  3. 操作者反馈维修，工单转 `reinspection_requested`；复检运行的任务 `m-e4c9282360aa` 再次审批并飞行。

  两个运行都 `completed`。两次飞行（代次 24、25）的监管者裁判在线与回放一致，错误成功 0；权威 flight.json 与任务、版本、代次、时间和 SHA 一致。

## 已知限制

- 一个服务进程一个引擎；多 worker 的 fencing 只在 S0 用例中验证，跨主机执行属于 P3 之后的重估。
- 分析是脚本夹具与确定性颜色特征：脚本夹具对同一资产总给出相同答案，复检分析不说明维修是否有效。真实分析器、识别质量与关单属于 P4。
- 排班在常驻任务台默认停用；S0 以逻辑时钟验证到期、窗口内重启与越窗停机，没有真实墙钟的长时间排班（P5 的 72 h 长稳）。
- 草案只返回、不保存、不可激活；把草案变成模板必须经版本化配置评审与新的目录摘要。
- 常驻任务台只有一个逻辑机场与一台 PX4 SITL；入口覆盖 HTTPS / API / WebSocket 帧，没有新增浏览器截图视觉验收。
- 常驻账本的审计增长（P1 既有行为，本次迁移时量到）：逻辑机场每秒一份状态报告，每份受理都写一条 `status.accepted` 审计。P1 激活后 3.6 h 内约 1.3 万行，账本从 2.55 MB 增到约 6.4 MB，折合约 26 MB / 天。P2 不改这一行为；保留或压缩策略在 P5 长稳之前，按 D056 / D058 的重估触发器（数据量使单文件备份窗口不可接受）另行设计。

## P3 / P4 接手物

- 运行、节点与 outbox 的持久边界，以及租约与 fencing；
- 触发去重与排班；
- 任务桥接（请求者、活动键、对账查询）与取消代次；
- 工单与复检链接；
- 带来源标注的分析记录与复核记录；
- 单机 S1 工作流执行器与完整回执。

P3 的多资源分配与时空预约沿用同一账本与串行化边界，新增表仍须先设计并获批准。P4 在此基础上接入真实分析器、发现去重与关单。P2 完成不证明多机调度、VLM 识别、复检关单质量或机场硬件已就绪。
