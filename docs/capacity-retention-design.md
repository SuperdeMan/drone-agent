# 容量观测与数据保留设计（WP-P6-07）

**状态**：设计（2026-10-12）。用户 2026-10-12 批准本工作包的索引与保留策略（「下一步要做的我批准」），按 D085 实施。表结构变更见 §5。§6 的评测方案在任何阶梯测量之前写定，并随预登记冻结。

## 1. 结论

- **常驻任务台账本的现状**（2026-10-12 只读统计）：
  - 1.17 GB，其中 `op_events` 约 0.92 GB（360 万行）；
  - `op_events` 的 98.8% 是机场状态报告被接受时写的 `status.accepted`。10-03 起四个机场每天约 31.4 万行（每秒 3.6 行），账本每天约增长 90 MB（含索引）；
  - 从未有任何保留或归档。
- **热路径查询随历史线性变慢**（同一账本上实测，只读）：
  - 按任务读执行事件全表扫描并排序，31.5 ms。它出现在每轮后台处理与每次任务视图里，P5 长稳排查时 666 个任务累计扫描 2566 次、共 17.2 s；
  - 审计列表每页扫描 2 万行（35.5 ms），其中绝大多数是机场状态行；
  - 最近任务列表每收一条机场报告调用一次，目前 1 ms，随任务数线性增长。
- **稳态语句清单**（§6 的阶梯工具在 1× 合成账本上跟踪一个稳态窗口内服务执行的全部语句并取查询计划）另外找出：
  - 每轮：待领取任务包、活动预约、活动工作流运行三条读取都扫描全表；
  - 每次任务刷新：证据、核验、事实、问题按任务读取都扫描全表，任务视图还读出所在机场的全部动作再在内存中筛选。启动时每个任务都要刷新一次，因此启动核对随历史平方增长；
  - 机场资源视图读出全部动作只取最后 20 条。
- **16× 账本上的重放计时**（同一工具在 16× 合成账本上跑一段稳态，记录全部语句后逐条重放计时）又找出走索引、但读出全部历史再排序截取的读法：
  - 审计列表的请求、审批与操作请求三个来源（16× 时 33 / 55 / 21 ms）；
  - 任务单列表读出项目全部任务单（64 ms），机器人活动分配读出该机器人全部分配；
  - 资源视图的机场最新预约（15 ms），业务作业按项目、按发现、按运行读取（72 ms 等），工作流的子运行与出站消息按运行读取；
  - 厂商网关每次启动重建未结束任务时读出全部厂商日志（一次 0.35 s），见 §3.1「不改」。
- **建议**：
  1. 一次带标记的迁移加 19 个索引，工作流、调度与业务表上另有 6 个后置索引，并改写若干随历史增长的读取；
  2. `status.accepted` 超过保留期的行归档成可校验的压缩文件后移出账本，其他审计事件一律不动；
  3. 服务内记录容量指标（后台处理耗时、事务耗时、事件循环延迟、接口尾延迟、队列积压），经只读接口与周期快照提供；
  4. 用规模阶梯（合成账本 1× / 4× / 16× 历史）测启动、核对、每轮处理与接口的趋势，判据在测量前写定并预登记。

## 2. 现状要点

- **写入**：`status.accepted` 每接受一条机场报告写一行（`fleet/docks.py`），4 个机场约每秒各报一次。P1 裁判按「领取前最后一条被接受的报告」核对领取条件，所以写入不能去重。
- **读取**：
  - 后台每 0.5 s 一轮。对每个占用中的预约要读本活动的事件、本任务的领取与执行事件；每收一条机场报告读一次最近 50 个任务。
  - 每次任务视图（以及每次刷新）读本任务的执行事件、证据、核验、问题、投递与派遣事件。
  - 多数读按 `mission_id` 过滤，但对应表没有以它开头的索引。
- **迁移**：各存储的迁移都在打开时核对标记、带备份与演练（D056–D064）。`desk-cloud --apply` 先在账本副本上依次演练再迁移真实账本。账本打开时就执行的建表语句不能加新索引，否则 D056 的演练会因 dump 不同而失败。
- **观测**：服务的 `health` 只有静态身份。长稳采样每 60 s 记录容器资源、账本字节数与若干表的行数。长稳裁判没有趋势判据，而且要求增长表行数不下降。

## 3. 设计

### 3.1 索引（容量迁移 `meta.capacity_schema = 1`）

新增一个迁移步骤（`fleet/capacity_store.py`），所有对象用 `cap_` 前缀，使各存储按前缀核对名单的演练互不干扰。与 D056–D064 相同：
- 已有数据的库先在线备份，并校验完整性与逐表行数；
- DDL 与标记在同一事务内提交，失败就回滚并拒绝启动；
- 只在服务带 `--catalog` 启动时执行，此时工作流、调度与业务存储还没打开，这些表上的索引作为后置索引处理（见下）；
- 不改任何表与列，`schema_version` 仍为 2。

| 索引 | 服务的查询 |
|---|---|
| `cap_events_mission ON events(mission_id, mission_version, journal, seq)` | 按任务（与版本）读执行事件并排序 |
| `cap_missions_created ON missions(created_at)` | 最近任务列表（每条机场报告一次） |
| `cap_deliveries_mission ON deliveries(mission_id, cursor)` | 按任务读投递 |
| `cap_deliveries_open ON deliveries(cursor) WHERE acked_at IS NULL` | 机器人拉取未确认投递、每轮扫描待领取的任务包（两者都只读未确认的少数行） |
| `cap_op_events_audit ON op_events(id) WHERE kind NOT IN ('status.accepted','lease.taken','node.state')` | 审计列表按 SQL 过滤噪声并分页 |
| `cap_op_reservations_dock ON op_reservations(dock_id, state, updated_at)` | 每轮每个机场找最近释放的活动 |
| `cap_op_holds_reservation ON op_holds(reservation_id)` | 每个预约读其持有 |
| `cap_op_claims_mission ON op_claims(mission_id)` | 每轮按任务读领取 |
| `cap_op_reservations_state ON op_reservations(state, created_at)` | 每轮读活动预约 |
| `cap_evidence_mission ON evidence(mission_id, mission_version)` | 每次刷新读证据 |
| `cap_verifications_mission ON verifications(mission_id)` | 每次刷新读核验 |
| `cap_facts_mission ON facts(mission_id)` | 每次刷新读事实 |
| `cap_issues_mission ON issues(mission_id)` | 每次刷新与视图读问题 |
| `cap_op_dock_actions_open ON op_dock_actions(dock_id, state, requested_at)` | 机场后端拉取待处理动作 |
| `cap_op_dock_actions_dock ON op_dock_actions(dock_id, requested_at)` | 机场资源视图取最新 20 条动作 |
| `cap_requests_received ON requests(received_at)` | 审计列表按时间倒序读请求 |
| `cap_versions_updated ON versions(updated_at)` | 审计列表按时间倒序读审批与驳回 |
| `cap_deliveries_requests ON deliveries(created_at) WHERE kind = 'operator_request'` | 审计列表读操作请求；只含操作请求，使每轮的任务包扫描仍走 `cap_deliveries_open` |
| `cap_op_reservations_recent ON op_reservations(dock_id, created_at)` | 机场资源视图取最新 20 条预约 |

- **后置索引**：下面 6 个建在工作流、调度与业务存储的表上。全新账本上这些表在容量步骤之后才建立，所以容量迁移只建表已存在的；服务每次启动在全部存储建立之后再执行一次收敛（`converge`），为新出现的表补建，只建索引、不改数据。任务台账本上这些表早已存在，迁移时一并建立。

| 后置索引 | 服务的查询 |
|---|---|
| `cap_wf_runs_started ON wf_runs(started_by, created_at)` | 运行的子运行（复检） |
| `cap_wf_outbox_run ON wf_outbox(run_id, created_at)` | 按运行读出站消息 |
| `cap_sc_assignments_state ON sc_assignments(state, robot_id)` | 任务单列表中各机器人的活动分配 |
| `cap_bz_jobs_project ON bz_jobs(project_id, created_at)` | 业务汇总的最近作业 |
| `cap_bz_jobs_requester ON bz_jobs(requested_by, created_at)` | 运行的分析作业 |
| `cap_bz_jobs_finding ON bz_jobs(finding_id, created_at)` | 发现的作业 |

- **审计列表**：改为用 `cap_op_events_audit` 分页读取非噪声行，不再每页扫描固定的 2 万行窗口。返回格式与游标含义不变。
- **读取改写**（结果与顺序不变）：
  - 活动工作流运行由 `state NOT IN (终态)` 改为列出仍在运行的状态，使既有的 `wf_runs_state` 索引能用上；
  - 任务视图的机场动作按活动键范围 `mission:<id>:` 读取，不再读出机场全部动作后在内存中筛选；
  - 机场资源视图的最新 20 条动作与预约按时间倒序各取 20 条，不再读出全部；
  - 任务单列表分两次读取：未结任务单走状态索引，已结束的只取最新 30 条；有状态过滤的任务单与分配查询以 `+project_id` / `+robot_id` 使查询计划走状态索引；
  - 审计列表的三个来源各自按时间索引倒序读取、取满一页即停，以 `+b.project_id` 避免从项目全部绑定出发。
- **不改**：厂商网关每次启动从账本重建未结束的任务，要读出全部厂商日志再按链核对（16× 时查询 0.35 s，只在启动时一次）。只读未结束任务需要改变「未结束」的判定依据，不在本工作包内，列为接手项。

### 3.2 `status.accepted` 的保留与归档

- **范围**：只处理 `kind = 'status.accepted'` 的行；任务、审批、预约、领取、取消、动作、工作流、任务单、业务与审计事件永远留在账本。
- **保留期**：服务参数 `--status-retention-days N`，缺省不归档，以保持 S0 / S1 与旧部署的行为。任务台设为 7 天。
- **归档单位**：按 UTC 日写 `<state>/archive/op_events/status-accepted-YYYYMMDD.jsonl.gz`，每次追加一个 gzip 成员，每块至多 2000 行。
  - 成员内是完整行，即 `id`、`subject`、`kind`、`actor`、`body`、`created_at`。
  - 写入并 fsync 之后，在同一事务里登记清单行，并删除这些 id 的行。
- **每次调用的工作量有上限**：`created_at` 没有索引，若按时间直接筛选，追平之后每一轮都要扫描保留窗口内全部较新的状态行（约 220 万行）。因此：
  - 服务按时间顺序写入 `op_events`，归档按 id 二分查找截止时刻之前的最后一行（只用 rowid 查找），只读这段 id 范围；时钟回拨而落在 id 之后的行会被跳过，不会丢失；
  - 每次调用至多读取 2 万个 id 的窗口：状态行稀疏时（例如两段状态行之间隔着大量其他事件）也不会一次读很远；没有状态行的窗口记为已扫过，下一次调用接着读；
  - 只归档完整的块：满 2000 行，或该日已结束（截止时刻已过该日，或下一条状态行属于下一日），或其窗口在截止时刻之前结束；
  - 在截止处没有完整的块，就休息 30 s；已归档的游标只在启动时读一次。
- **清单表**：`cap_event_archives(chunk_id, kind, file, offset, length, first_id, last_id, rows, first_at, last_at, sha256, created_at)`，见 §5。每块可以按偏移与长度独立解压，并用 SHA-256 核对。
- **节奏**：每轮至多处理一块。部署时任务台约有 150–200 万行早于 7 天（取决于部署日期），按每块 2000 行、每 0.5 s 一轮，约 10 分钟追平。
- **失败处理**：
  - 文件写成功但事务失败，留下的是孤立块。下次运行先按清单核对文件尾，截掉未登记的尾部，再续写。
  - 事务成功的块不会被重复归档。
- **不做**：自动 VACUUM。归档后释放的页由新写入复用，文件不再增长；需要收缩时，由运维在停机窗口执行，见运维指南。
- **读取工具**：`fleet/archive.py` 提供按清单逐块读出与校验，供裁判、导出与人工核查使用。
- **长稳判据的调整**：「增长表不下降」对 `op_events` 改为「`op_events` 行数加已归档行数不下降」。其余判据不变。

### 3.3 容量指标

- **服务内**（`fleet/capacity.py`），在内存中按 5 分钟窗口统计 p50 / p95 / p99 / max：
  - 每轮后台处理的总耗时与各部分耗时（派遣、工作流、调度、分析、厂商、刷新、启动核对片段、归档）；
  - 写事务耗时（最外层 `transaction()`）；
  - 事件循环延迟（专门的 0.2 s 探针的超时量）；
  - 接口每个方法的耗时（`api.dispatch` 内计时）。
- **队列积压**（至多每 10 s 读一次，便宜的计数）：待刷新与启动核对队列长度、未确认投递、排队任务单、可运行分析作业、待发出的工作流消息、待处理机场动作、已归档行数与账本字节数。
- **提供方式**：
  - 只读接口 `capacity.get`（项目管理员，`RESOURCE_MAINTAIN`）返回当前窗口统计与积压，并加入授权矩阵；
  - 服务每 60 s 把同样内容追加到 `<state>/capacity/capacity-YYYYMMDD.jsonl`，只保留 14 天；
  - 长稳采样器同时记录已归档行数，长稳裁判据此核对 `op_events` 的守恒。

## 4. 不变量

- 归档只移出 `status.accepted` 行。每一块移出之前，其内容已写入归档文件、fsync，并在同一事务里登记清单；任何时刻，账本行加归档块就是完整的状态报告记录。
- 迁移不改表与列，失败回滚并拒绝启动。D056–D064 的演练与 `desk-cloud --apply` 的副本演练全部通过。
- 三处读取改写返回相同的行与顺序。
- 指标只读：指标与快照不写账本，不影响任何判定。
- 保留期缺省关闭；S0 / S1 与历史门禁的行为不变。

## 5. 表结构变更（用户已批准）

- **新增 1 张表**：`cap_event_archives`，即归档清单，每块一行。
- **新增 25 个索引**：19 个基础索引与 6 个后置索引，见 §3.1。最初设计 8 个；实施中稳态语句清单找出 7 个、16× 重放计时找出 4 个基础索引与 6 个后置索引，同属这一次容量迁移，部署前加入。
- **新标记**：`meta.capacity_schema = 1`，及 `capacity_migrated_at`、`capacity_backup`。

不改任何既有表与列，`schema_version`、`workflow_schema`、`scheduling_schema`、`business_schema` 不变。旧版本代码可以直接在迁移后的库上运行，因为它不认识的索引与表不影响它。

## 6. 评测（测量前写定，随预登记冻结）

工具为 `python -m drone_agent.eval.capacity_growth`，各部分在本机以高 QoS 运行（`scripts/high_qos`）。

- **模板**：在 S0 任务台世界（任务台四个目录，逻辑机场与飞行器）中逐个飞 9 个运行，模板账本不带 D085 对象：
  - 机队 `fleet_watch` 6 个，两架飞行器各 3 个资产；
  - 厂商 `vendor_watch` 2 个；
  - 园区 `appearance_watch` 1 个。S0 园区分析器把资产判为疑似，复核人驳回，因此不留未结的发现或工单。
- **生成**：
  - 规模为任务台 2026-10-12 的 1291 个任务的 1× / 4× / 16×，按任务台项目构成（机队 740、厂商 343、园区 208，30 个未绑定的 M2 任务计入园区）；时间跨度为任务台的 19 天乘以规模；
  - 每个运行的全部行按实例 id 求闭包后克隆（调度决定里记录的机场动作只作快照引用，不连接两个运行）。克隆替换全部实例 id，平移到等距时间槽，并按服务的算法重算任务包哈希、溯源封印、执行日志哈希链与事件 id、报告的溯源摘要；证据沿用模板媒体；
  - 模板自身的行原地移到历史开头；最后 7.5 天的被接受机场报告（每天 31.4 万行，按任务台各机场频率）按时间与克隆交错写入，全库按时间有序；
  - 生成是确定性的：同一模板与种子得到逐字节相同的账本。模板与三个账本的摘要写入预登记。
- **自检**：每个规模在副本上让服务刷新 9 个模板任务与 300 个抽样克隆，不得写入任何一行。
- **测量**（每个规模、每个变体一个独立进程，按 1×、4×、16× 的顺序，每个规模先 `indexed` 后 `plain`；前后各测一次固定 CPU 基准）：
  - `indexed` 先做容量迁移（计时，含备份），`plain` 不做（对照）；
  - 启动：构建服务到第一轮后台处理完成；
  - 启动核对：全部任务的刷新，记录每次刷新耗时；对照组上限 15 分钟，超时清空剩余队列，只报告已核对部分；
  - 归档（只 `indexed`）：核对完成后开启 7 天保留期，时钟固定在窗口末端，移出最旧的半天（约 15.7 万行）；
  - 稳态窗口 10 分钟：机场每秒报告、飞行器每秒同步；每 2 分钟启动一个机队巡检运行并审批；每秒一次接口探测（任务视图、任务列表、审计列表、任务单列表、工作流列表，按项目轮换）。
- **判据**（只看 `indexed`；`plain` 作为对照报告）：
  1. 稳态每轮耗时 p95：16× ≤ max(1.5 × 1×，1× + 10 ms)；
  2. 五个接口各自的 p95：16× ≤ max(2 × 1×，1× + 10 ms)，且 ≤ 200 ms；
  3. 启动核对：16× 不触顶，且每次刷新的平均耗时 ≤ max(1.5 × 1×，1× + 1 ms)；
  4. 机场报告入账 p99：每个规模 ≤ 100 ms；
  5. 归档：每个规模守恒（迁移前的状态行 = 剩余 + 已归档）、各块摘要核对通过、剩余到期行不足一块，归档期间每轮耗时 p99 ≤ 100 ms；
  6. 测量期间没有新增服务问题（`issues`）。
  - 绝对余量（10 ms、1 ms）避免小数值上的噪声把比值放大。
- **有效性**：六次测量齐全；模板、生成账本与代码摘要与预登记一致；全部 CPU 基准在其中位数的 1/1.5–1.5 倍之内（没有降速）；接口探测全部应答；稳态窗口满 10 分钟。无效则作废并披露，按同一预登记重跑。
- **回归**：P1–P6 S0 与授权矩阵当场重跑；长稳裁判单元测试通过。
- **任务台**：
  - 激活时在副本上演练全部迁移，并迁移真实账本；
  - 观察首次归档追平、`capacity.get` 可读、重启后的启动核对时长，入口核对通过；
  - 72 h 长稳不在本工作包内运行，需要时另行安排。

## 7. 不做

- 写入时去重机场报告：会改变 P1 裁判核对领取条件的依据。
- 把机场报告移到单独的表：要迁移现有 360 万行，并改动所有裁判与导出，收益与归档相同。
- 自动 VACUUM：会长时间锁库，影响机场报告的新鲜度。
- 对其他事件做保留：数据量小，而且是审计记录。
